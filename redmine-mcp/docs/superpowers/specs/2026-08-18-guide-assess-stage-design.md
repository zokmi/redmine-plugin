# 概述骨架精簡與 assess 註記模板 — 設計

日期：2026-08-18

## 問題

四份指南目前把所有章節都放在概述（`description`），只有臭蟲單的診斷段落例外。這造成三個問題：

1. **概述長度與章節數不一致。** `change` 有五章（三必填、兩選填）、`feature` 有六章
   （三必填、三選填）、`bug`+`report` 有五章（四必填、一選填）。概述是給非 IT 人員看的入口，
   卻是四份文件裡最容易膨脹的地方。
2. **選填章節的性質與概述不符。** `影響範圍`、`影響範圍與相依`、`不在範圍內` 三者要回答的是
   「既有資料怎麼處理」「相依哪張單」「哪些明確不做」——這些多半是接手的人查得出來、
   而非開單當下就知道的事實。`待確認` 亦然：內容常在需求方回覆後才定案。
3. **指南自己留了一個洞。** `change.md` 的 `影響範圍` 明寫「答不出來就整段拿掉留給 RD 補」，
   但套件裡沒有任何地方告訴 RD 補的時候該長什麼樣子。等於把責任交出去卻沒交格式。

目標：**`change` 與 `feature` 的概述只留必填章節；查得出事實的人另有一份註記模板可依循。**

範圍限定在這兩份單別：`bug`+`report` 的唯一選填章節 `佐證` 決定留在概述（理由見取捨表），因此問題 1 的章節數不一致只收斂到「三章 vs 四章」，不追求四份完全等長。強行對齊會動到 `bug` 的必填章節，代價高於收益。

  「目前只有臭蟲單」改完即為假，必須一併改寫。**

## 已決定的取捨

| 決策 | 選擇 | 理由 |
| --- | --- | --- |
| 統一程度 | **只砍選填章節，必填章節一字不動** | 對既有單子最相容，且必填章節的語感（`重現步驟` vs `調整內容` vs `需求內容`）本身就是單別的辨識點，統一成通用章節名會讓三種單子讀起來一樣 |
| 搬哪些章節 | `影響範圍`（change）、`影響範圍與相依`／`不在範圍內`（feature）、`待確認`（兩者） | 都是「有事實才寫得出來」的內容 |
| `佐證` 留在概述 | **不搬** | 那是回報者手上就有的東西，且附件在 Redmine 畫面上本來就與概述一起顯示，搬走反而拆散 |
| 承載 primitive | **擴充既有 `stage` 參數** | 白名單已是表格；模型只需維持「stage 決定落點」一條規則，不必學第二套機制 |
| 階段值命名 | **`assess`** | 要傳達「接手後查得出來的評估」。不沿用 `diagnose`（那是讀過原始碼寫根因，深度不同）；不用 `followup`（只講時序不講內容） |
| `stage=None` 的行為 | **維持回傳概述骨架** | 現有 `kind="change"`／`kind="feature"` 的呼叫完全不受影響，這次是純增量 |
| 模板配置 | **change 與 feature 各一份** | 兩者要回答的問題不同：change 的重心是「既有資料怎麼處理」，feature 的重心是「相依單號與範圍排除」。分開寫才給得出到位的提示詞 |
| 搬移的散文 | **移進註記模板，不刪除** | 「這一項最常被漏掉，卻最常在上線後炸開」這類提示是原文最有價值的部分，不可隨章節消失 |
| 空註記 | **模板明文禁止** | 註記會通知關注者；沒有事實可寫時追加一則空模板比不寫更擾人 |
| `bug` 的兩份指南 | **一字不動** | 沒有章節搬移，`diagnose.md` 本來就落在註記 |

落點規則因此從「三者＋一個例外」收斂成一條通則，寫進所有相關工具說明：

> **有 stage 後段的一律填 `add_issue_note` 的 `notes`，沒有 stage 的填 `description`。**

一條規則涵蓋六種組合，對模型少一個要背的特例。

## 被否決的方案

- **四種單別共用同一組章節名**（如 現況／要什麼／怎麼算完成）。最一致，但 `重現步驟`
  塞不進通用章節，且讀者失去從章節名判斷單別的線索。
- **新增正交參數 `target: description|note`。** 落點最直白，代價是 kind × stage × target
  三維並產生無效組合（`bug`+`diagnose`+`description`），驗證分支與錯誤訊息各多一層。
- **不改參數，概述骨架與註記模板一起回傳。** 程式最省事，但每次呼叫都多一份，
  PM 寫第一版時也拿到 RD 模板——與本次「精簡」的目標相反，並模糊掉整個設計賴以成立的落點規則。
- **change 與 feature 共用一份 assess 模板。** 章節取聯集後提示詞必然變泛，
  且 change 永遠會看到一個用不到的 `不在範圍內`。
- **在概述的 `調整內容`／`需求內容` 補一句「需求方已知的相依可寫在這裡」。**
  這會把剛砍掉的內容從後門放回概述。已知代價：需求方在對話裡順口提到的相依，
  開單當下沒有地方放，須由人另追一則 assess 註記。接受這個代價，換概述短而齊一。
- **把六份文案轉成 Claude Code plugin skill。** 2026-08-18 另做過分析：MCP 協定沒有 skill
  primitive（2026-07-28 版仍只有 tools／prompts／resources），skill 靠 plugin 散佈到 agent
  本機，會重現 2026-08-11 spec 已解掉的兩個問題（只在本機生效、與 server 版本漂移）。
  格式規範與消費它的 `create_issue` 驗證邏輯必須同套件同版號。

## 工具介面

`get_issue_guide(kind, stage=None)` 的六種合法組合：

| 呼叫 | 回傳 | 落點 |
| --- | --- | --- |
| `kind="bug", stage="report"` | 回報階段骨架（不變） | `description` |
| `kind="bug", stage="diagnose"` | 診斷模板（不變） | `notes` |
| `kind="change"` | 概述骨架（三章全必填） | `description` |
| `kind="change", stage="assess"` | 評估註記模板（新） | `notes` |
| `kind="feature"` | 概述骨架（三章全必填） | `description` |
| `kind="feature", stage="assess"` | 評估註記模板（新） | `notes` |

`stage` 的參數說明改寫為：`bug` 必填（`report`／`diagnose`）；`change`／`feature` 可選，
省略得到概述骨架、給 `assess` 得到註記模板。判準沿用現行原則——**依你手上有什麼事實，
不是依你的角色**。

四種錯誤各自列出合法值，訊息要能讓模型自行修正而非重試同一組參數：

1. `kind` 不在白名單。
2. 必填階段的單別缺 `stage` 或給了非法值。
3. 可選階段的單別給了非法 `stage`（例如 `change`+`diagnose`）。
4. 無階段的單別多帶 `stage`（改完後此類為空，分支保留以免日後新增單別時漏掉）。

## 實作

`_STAGED_KINDS` 現行語意是「這個 kind **必須**給 stage」，無法表達可選。拆成兩張表：

```python
#: 必須指定階段的單別：缺 stage 就報錯。
_REQUIRED_STAGE_KINDS: dict[str, tuple[str, ...]] = {"bug": ("report", "diagnose")}

#: 可選階段的單別：stage=None 回傳概述骨架，給了合法階段才回傳註記模板。
_OPTIONAL_STAGE_KINDS: dict[str, tuple[str, ...]] = {
    "change": ("assess",),
    "feature": ("assess",),
}
```

`_GUIDE_FILES` 新增兩筆：

```python
("change", "assess"): ("redmine_mcp.guides.change_request", "assess.md"),
("feature", "assess"): ("redmine_mcp.guides.feature_request", "assess.md"),
```

`_VALID_KINDS` 仍由 `_GUIDE_FILES` 推導，不另維護第二份清單。驗證順序依上節四種錯誤排列。
`stage` 來自模型，一律經白名單查表，**絕不拼進路徑**——沿用現行的路徑穿越防護。
讀檔仍在模組載入時一次完成，讀不到就讓模組載入失敗。

## 註記模板內容（`assess.md` ×2）

結構比概述指南輕，五段：

1. **定位** — 三件事必須明寫：填入 `add_issue_note` 的 `notes`，**不要動概述**
   （那是需求方的入口，覆寫掉等於把非 IT 讀者趕走）；**沒有事實可寫就不要追加註記**；
   這份模板**不限 RD**，需求方自己知道相依單號時同樣適用，判準是手上有沒有事實。
2. **骨架**（章節名不帶「（選填）」後綴，改以定位段的「沒有事實就不要寫」統一交代）
   - `change_request/assess.md`：`## 影響範圍`、`## 待確認（需求面）`
   - `feature_request/assess.md`：`## 影響範圍與相依`、`## 不在範圍內`、`## 待確認（需求面）`
3. **各章節怎麼寫** — 由概述指南搬過來的散文，維持原文的具體提示。
4. **送出** — `add_issue_note`，不覆寫 `description`；標題若需修正另走 `update_issue` 只帶 `subject`。
5. **自我檢查** — 三到四項，含「沒有為了填滿而猜」與「沒有動到概述」。

排版與語氣沿用四份既有指南：Markdown、章節 `##`、全篇繁體中文、程式碼與欄位名原樣、
半形括號留給程式碼。
