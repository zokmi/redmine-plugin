# 臭蟲單格式指南分階段（回報／診斷）— 設計

日期：2026-08-12

## 問題

現行的內建指南（`get_bug_report_guide` 回傳的 `bug_report.md`）預設寫單的人讀過原始碼：
它要求檔案路徑加行號、程式碼片段、根因分析，以及帶判準的建議修正。

PM、客服、測試人員發現問題時，這些一項都給不出來。結果是他們要嘛不用這個格式，
要嘛硬填而寫出看似完整、實則沒有依據的內容——後者比不用格式更糟，因為錯誤的行號
與臆測的根因會把接手的 RD 帶往錯的方向。

目標：**讓沒有程式碼層級事實的人也能開出一張 RD 不必回頭追問的單。**

## 已決定的取捨

| 決策 | 選擇 | 理由 |
| --- | --- | --- |
| 兩份格式的關係 | **同一張單、分階段填** | PM 先寫現象與影響，RD 診斷後往下追加根因與建議修正 |
| 交付形式 | **同一個工具加 `stage` 參數** | 不增加工具數量；模型依情境選擇，判準寫在工具說明裡 |
| `stage` 預設值 | **無預設，必填** | 見下節 |
| 簡易版的形態 | **同骨架瘦身版** | 沿用【】章節與分隔線，RD 續寫時不必重排前段 |
| PM 階段必填 | 重現步驟、發生環境與時間、影響與急迫度、佐證 | 由使用者指定；四項同時是章節骨架與自我檢查清單 |
| `diagnose.md` 內容 | **一字不改** | 現行全文剛通過完整審查，本次只搬移位置 |

被否決的方案：

- **問答式表單。** PM 最好上手，但同一張單會出現兩種格式語言（PM 段問答、RD 段章節），
  接手時得整段重寫才能統一，直接打到「同一張單分階段」這個決定上。
- **極簡三行（標題＋現象＋影響）。** 最省 PM 的力氣，但重現步驟與環境時間都沒了，
  RD 幾乎一定要回頭問——而那正是把這些列為必填要避免的事。
- **兩個獨立工具。** 工具數變 18，且工具名本身無法承載「依你手上有沒有程式碼事實而定」
  這個判準，模型選錯的機會反而更高。
- **一份文件兩個章節。** 最省事，但 PM 情境仍會讀到大量工程內容，等於沒有簡化。

## 工具介面

```python
async def get_bug_report_guide(
    stage: Annotated[str, Field(description=...)],
) -> dict[str, str]:
```

`stage` 必填，只接受兩個值：

- `"report"` — 回報階段。給只觀察到現象、沒讀過相關原始碼的人。回傳簡易版。
- `"diagnose"` — 診斷階段。給已讀過原始碼、要寫出根因與建議修正的人。回傳現行完整版。

回傳形狀不變：`{"guide": "<Markdown 全文>"}`。工具仍為 `READ_ONLY`，仍不連任何站台。

### 為什麼沒有預設值

兩種預設都會在某一半的情境靜默降級：預設 `"report"` 時，工程端沒帶參數就拿到簡易版，
寫出來的單比現在差；預設 `"diagnose"` 時，PM 情境拿到一份要求行號與程式碼片段的文件，
等於這次改動沒發生。必填讓呼叫端每次都要看一眼自己是哪種情境——這個決定本來就該
有意識地做。

### 判準寫在工具說明裡

> 撰寫 Redmine 臭蟲單前必須先呼叫本工具取得格式。`stage="report"`：你只觀察到現象、
> 沒有讀過相關原始碼（PM／客服／測試回報）。`stage="diagnose"`：你已實際讀過原始碼、
> 要寫出根因與建議修正。判斷依據是**你手上有沒有程式碼層級的事實**，不是你的角色。

最後一句是關鍵：以「手上有什麼事實」而非「你是誰」當判準，因為模型不知道自己代表誰，
但一定知道自己有沒有讀過程式碼。

`server.py` 的指路句與 `create_issue` 的說明同步加上參數提示，兩處措辭仍維持一致。

## 簡易版（`report.md`）內容

### 標題

```
<受影響的功能>：<使用者遭遇的後果>
```

兩段，不含技術根因——那是 PM 給不出來的部分。文中註明 RD 診斷後可補上機制，
改寫成完整版的三段句型。

範例：`客戶匯出對帳報表：金額比實際少，財務無法對帳`
反例：`報表有問題`（沒有功能、沒有後果，逼人點進來才知道嚴不嚴重）。

### 骨架

四章節，分隔線沿用同一條 60 個半形連字號：

```
【問題描述】
<一兩句：哪個功能、什麼情況下、發生什麼事>

【重現步驟】
環境：<正式站／測試站，網址>
對象：<哪個帳號、哪個客戶>
時間：<發生時間>
1. <操作>
2. <操作>
3. 預期看到：<...>
   實際看到：<...>

【影響與急迫度】
- 誰受影響、大約多少人
- 多常發生（每次／偶爾／只發生過一次）
- 有沒有替代做法可以先擋著
- 有沒有資料被寫錯或遺失

【佐證】
<截圖、錯誤訊息原文、相關單號或訂單編號>
```

### 三個寫作規則

取代完整版的工程要求：

1. **允許並鼓勵寫「未確認」。** 不知道就標明不知道，不要猜也不要留白——留白會讓 RD
   以為你檢查過了。
2. **「預期看到」與「實際看到」必須分開寫。** 只寫「不對」是最常見的無效回報；兩者並列，
   RD 才知道你認定的正確行為是什麼，有時分歧就在這裡。
3. **不要診斷。** 不必猜是哪支程式、哪個欄位壞了。猜錯會把 RD 帶往錯的方向，比不猜更糟。

### 與完整版規則的一處衝突

完整版寫「空章節比沒有章節更浪費讀者時間」。簡易版因此**不預留**【根因】【建議修正】
的空標題，改在文末寫一句「根因與建議修正由接手的 RD 診斷後補上」——維持原規則，
同時把分階段的意圖說清楚。

### 自我檢查清單

五項：標題兩段齊全、重現步驟帶環境與時間、預期與實際分開寫、影響評估誠實、佐證附上。

### 篇幅

目標約完整版的三分之一（完整版 4200 字）。

## 檔案結構

一個主題一個目錄、一個階段一個檔：

```
src/redmine_mcp/guides/
  __init__.py
  bug_report/
    __init__.py    # importlib.resources 需要它才能把目錄當套件讀
    report.md      # 新寫
    diagnose.md    # 由現行 bug_report.md 原樣搬移，內容一字不動
```

## 實作

`stage` 來自模型，**絕不可**直接拼進檔案路徑——那是路徑穿越漏洞。改用凍結的白名單對照表：

```python
_GUIDE_FILES = {"report": "report.md", "diagnose": "diagnose.md"}

#: 兩份指南在模組載入時各讀一次。理由同前：檔案隨套件發佈，server 生命週期內不會變。
BUG_REPORT_GUIDES = {
    stage: (files("redmine_mcp.guides.bug_report") / name).read_text(encoding="utf-8")
    for stage, name in _GUIDE_FILES.items()
}
```

工具查表，查不到就拋出列有兩個合法值的錯誤——訊息要能讓模型自己修正，不可靜默
回傳其中一種。

錯誤處理原則沿用現行設計：檔案讀不到就讓模組載入失敗，不加後備空字串或 try/except。

## 測試

延伸 `tests/test_guide_tools.py`：

1. **兩個 stage 各回傳對應內容** — 用各自獨有的章節標記區分：`report` 含【影響與急迫度】
   且不含【建議修正】；`diagnose` 含【建議修正】且不含【影響與急迫度】。這比斷言字數可靠。
   已核對現行 `bug_report.md`：它含【建議修正】、不含「影響與急迫度」字樣，前提成立。
   注意斷言的是**帶全形方括號的標記**——簡易版文末那句「根因與建議修正由接手的 RD
   診斷後補上」含「建議修正」四字但無方括號，不會誤觸。
2. **無效 stage 拋錯**，且錯誤訊息同時含 `report` 與 `diagnose`。
3. **禁用字眼測試對兩份都跑**（不含 `mcp__redmine__`、`ToolSearch`、`references/example`），
   以 pytest 參數化涵蓋兩個 stage。
   **去識別化的正向斷言只跑 `diagnose`** — 那幾個虛構名稱（`cStepDone` 等）是完整版
   範例特有的，簡易版的範例（對帳報表、登入頁）本來就不含任何專案識別字，
   對它斷言這些名稱會恆假。簡易版的防護來自它根本沒有引用任何實際系統。
4. **打包測試改為兩個檔案都檢查** — 新增子目錄是打包最容易漏的地方。
5. 工具數維持 17（只加參數、不新增工具），`test_server.py` 不受影響。

## 文件

README 與 SETUP 的 `get_bug_report_guide` 那條加上 `stage` 的兩個值與判準；
README 那段補一句分階段填寫的用法。

## 不在範圍內

- 不改 `diagnose.md` 的任何一個字
- 不新增工具、不改 `create_issue` 的行為或驗證邏輯
- 不為其他單別（功能單、需求單）新增指南
- 不在 server 端驗證使用者實際寫出來的內容是否符合格式
