# 判讀準則與常見誤判

比對時真正花時間的不是找檔案，而是判斷「這個異動算不算做到了」。這份文件收錄各類異動的
處理方式，以及最容易出錯的判斷。

## 各類異動怎麼歸屬

**改名／搬移（狀態 R）**
git 的 `-M` 已經偵測改名，`added`/`deleted` 會是實際內容差異而非整檔重寫。如果行數接近 0，
那是純搬移，通常不承載需求，歸為「結構性異動」而非漏做或範圍外的證據。但要留意搬移
會不會影響引用它的地方——檔案路徑變了而呼叫端沒改，是編譯過但執行炸掉的典型來源。

**格式化／自動排版**
整檔的縮排、換行、import 排序變動會製造大量雜訊，把真正的邏輯改動淹沒。看到某檔案增刪行數
接近且遠大於其他檔案時，先用 `git diff -w` 忽略空白重看一次，判斷是否純格式化。純格式化的
檔案在報告裡合併成一列說明即可，不要逐檔展開。

**共用程式（helper／service／interceptor／guard／base class）**
這類檔案的異動必須追呼叫端才知道影響範圍。用 `codegraph_explore` 查誰呼叫它，把呼叫端
回推到功能面。這一步不能省：共用程式是「改了 A 卻弄壞 B」的主要來源，而 B 通常不在單子上，
需求方也不會想到要測。

**設定檔（appsettings、environment.ts、web.config）**
要看**改了哪個鍵**，只寫檔名對讀報告的人沒有幫助。另外注意設定值的異動常常需要正式環境
同步調整，單子若沒提到這件事，本身就是一個值得指出的缺口。

**SQL 檔**
打開來看內容，摘出實際的 DDL/DML。SQL 是少數「單子沒提到但一定要執行」的異動類型——
漏執行的後果是正式環境直接壞掉，所以即使它落在範圍外也一定要在報告中列出。

**測試檔**
測試本身通常不是需求條目的實作證據，但**測試的缺席**可能是。見下方規範類查核條目。

**文件與建置檔（.md、docs/、package.json、.csproj）**
不影響正式環境行為。除非單子明確要求更新文件，否則歸為「不影響判定」，在報告裡一句話帶過。

## 常見誤判

**把 commit 標題當成實作證據**
最常見也最嚴重。標題寫「#94206 修正住戶已存在」而 diff 只改了一個變數名，這張單就是沒做完。
判定必須來自 diff 內容。

**檔案有改到就算做到**
一個 commit 動到五個檔案，不代表五個條目都完成了。要對到**具體的那幾行**在做那件事。

**把「相關」當成「滿足」**
單子要求「新增欄位並在列表顯示」，程式只加了 DB 欄位沒改列表。這是部分完成，判 ❌ 並寫明
做到哪、缺什麼——判 ✅ 會直接造成漏測。

**單子空白就判一致**
描述空、註解空，代表**沒有東西可以比對**，不代表程式沒問題。判 🔍 並說明需求來源不足。

**把範圍外異動一律當成問題**
順手修的 bug、重構、跟著改的相依處都很正常。範圍外的意義是「沒被需求方確認過、測試計畫
不會涵蓋」，所以要被看見；報告的語氣是提請注意，不是指控。

**跨 repo 的實作被誤判為漏做**
前後端分開的專案，單子的 UI 要求在另一個 repo。查核前先確認範圍涵蓋哪些 repo；只查了後端
就說前端沒做，是查核範圍的問題不是實作的問題，要標 ❓ 並註明「未涵蓋前端 repo」。

**用舊版檔案內容判斷**
判讀時看的是 diff 之後的狀態。如果直接讀工作目錄的檔案，讀到的可能是查核範圍之外的後續
修改。要嚴謹時用 `git show <commit>:<path>` 取該 commit 當下的內容。

## 判定為「一致」的門檻

判 ✅ 需要同時滿足：

1. 指得到具體位置（`檔案:行號` 或 `檔案` + 可辨識的函式名）
2. 說得出那段改動**如何**滿足這個條目，而不只是「有關」
3. 沒有明顯的殘留矛盾（例如條件改了但另一條分支還是舊行為）

任何一項做不到就是 ❓，不是 ✅。降低門檻換來的乾淨報告沒有價值。

## 反向查核：範圍外異動的分級

範圍外異動不是同一種東西，分開講才有用：

| 等級 | 特徵 | 報告方式 |
| :-- | :-- | :-- |
| 高 | 動到共用程式、設定、SQL、權限判斷 | 逐項列出，附影響範圍分析 |
| 中 | 動到其他功能的邏輯 | 列出檔案與一句話說明 |
| 低 | 格式化、註解、命名、文件 | 合併成一列帶過 |

沒帶單號的 commit（腳本輸出的 `unlabeled`）一律歸為需要指出的發現，即使內容看起來無害——
因為它繞過了單子的追蹤與驗收流程，這件事本身就值得讓 PM 知道。

## 這個專案的規範類查核條目

使用者若要求連同規範一起查（`CLAUDE.md` 的跨專案規則），這幾項可以直接從 diff 判定，
成本低而漏掉的代價高：

- **邏輯驗證要有單元測試**：後端 `App.BLL`／Service 層有規則判定、資格檢查、狀態轉換、
  計價計算的異動，卻沒有對應的測試檔異動 → 值得列為缺口。前端有邏輯的 service／component
  異動沒有 `*.spec.ts` 同步異動時同理（自動產生的 API client 不算）。
- **時間欄位存 UTC**：新增或修改時間欄位時出現 `DateTime.Now` 或 `AddHours(8)` → 違反
  「DB 一律存 UTC+0、讀取端才轉台北時間」的慣例。
- **匿名端點要有限流**：新增未套授權的端點（登入、OTP、驗證碼、webhook、登入前公開查詢）
  卻沒有 `[EnableRateLimiting(...)]` → 安全缺口。
- **公開結構要有中文說明**：新增欄位、DTO 欄位、介面欄位、公開方法或 helper 卻沒有中文
  註解／JSDoc。
- **欄位層級轉換要用宣告式**：在 service 迴圈裡逐筆改值做時區、格式化、遮罩、加解密 →
  應改用屬性上的 converter／pipe。

這些是規範查核，跟需求查核分開列在報告的獨立區塊，不要混進需求條目表——它們的處理優先序
和決策者都不一樣。
