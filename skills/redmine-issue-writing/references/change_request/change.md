# Redmine 調整單文案格式

調整單處理的是**既有功能要改成別的樣子**——設定值、規則、文案、版面、流程的異動。它不是臭蟲單：沒有壞掉的東西，只有「現在這樣，我們要它變那樣」。

一張好的調整單只有一個判準：**接手的人不必回頭問你，就知道要改哪裡、改成什麼、改完怎麼確認沒事。**

如果你發現自己在寫「這是錯的」「使用者受到影響」，那多半是臭蟲單而不是調整單，換一份格式寫。

## 標題

```
<受影響的功能／模組>：<改成什麼>
```

冒號前指出被動到的東西，冒號後直接寫異動本身，不要只寫「調整」「優化」這種空詞。

**範例：**

- `簡訊發送設定：API 端點由 http 改為 https`
- `訂單列表：預設排序由建立時間改為出貨日期`
- `密碼規則：最短長度由 6 碼提高為 12 碼`

反例：`調整簡訊設定`（改成什麼？看完標題還是得點進來）。

## 排版格式

單子內文一律用 **Markdown**，不要用 textile。`h3. 標題` 這類 textile 語法在 Markdown 站台會原樣顯示成純文字，反而更難讀。

- 章節標題用 `##`；靠標題階層分段，不要用連字號分隔線。
- 設定值、路徑、欄位名、程式碼一律用反引號或三個反引號的圍欄區塊。
- 條列用 `-`，有先後順序才用 `1.`。

## 內文骨架

前三章必填。**不要為了填滿而猜**——猜錯的內容會讓人以為有人確認過了，比留白更糟。

影響範圍不寫在這裡：那是查得出事實的人依 `references/change_request/assess.md` 的評估註記模板撰寫、追加在註記裡的內容。

**驗收標準與待確認一律留在概述。** 你只要列出自己確定的驗收條目，評估的人查到新判準時會接在同一章後面；〈待確認〉多半由評估後追加，開單時寫不出來就整段拿掉。理由是這兩章會被勾、被調整、被答覆，而註記實務上只能新增、改不動——放在註記只會愈積愈多份，讀的人不知道哪一份算數。

````markdown
## 現況與問題

<現在是什麼行為／什麼設定，為什麼要改——一兩句即可>

## 調整內容

<哪個畫面／哪條規則／哪個設定，從什麼改成什麼；逐項列出並給前後對照>

## 驗收標準

<可驗證的條列：誰做什麼動作，會看到什麼結果>

## 待確認（選填，多半由評估後追加）

<要需求方拍板才能定案的部分。開單時通常寫不出來，整段拿掉即可>
````

## 自我檢查

送出前逐項確認；每一項的展開說明在下面各節：

- [ ] 骨架整份寫在概述（`description`）欄位，沒有拆散到其他欄位
- [ ] 追蹤標籤與專案填的是查該站清單換到的 id，預計完成日是問出來的、不是自行推定的
- [ ] 標題兩段齊全（受影響的功能、改成什麼），不是「調整 XXX」這種空標題
- [ ] 內文是 Markdown：章節用 `##`，設定值用反引號或圍欄區塊，沒有 textile 語法或連字號分隔線
- [ ] 寫出了「為什麼要改」，不只是「要改什麼」
- [ ] 調整內容指名到畫面／設定項／欄位，且有調整前後對照
- [ ] 驗收標準每條都能一次判定通過或不通過，不是「測試功能正常」
- [ ] 概述沒有夾帶查得出來才寫得出來的事實快照（影響範圍留給 assess 註記）
- [ ] 〈待確認〉沒東西寫就整段拿掉，不留空標題（它多半由評估後追加）
- [ ] 沒有夾帶與本次異動無關的順手改動
- [ ] 必填內容都來自提出者提供或既有事實，缺的部分是問出來的，不是你補的猜測
- [ ] 沒有空章節，也沒有為了填滿而猜的內容

## 資訊不足時：用問答補齊

提出調整的人多半不是 IT。必填章節的資訊不夠時，**不要自己填、不要留白，也不要把骨架丟回去叫對方填**——直接在對話裡問。

- **一次只問一題**，問完等回覆再問下一題。一次丟五個問題，通常只會拿回第一題的答案。
- **盡量給選項**讓對方用選的，並且永遠留一個「不知道」。
- **用日常語言問，不要用章節名**。不要問「調整內容為何」，問「這個地方現在長什麼樣子？你希望改成什麼樣子？」；不要問「驗收標準」，問「改好之後，你會怎麼確認它真的改對了？」
- **影響範圍不問**。那是查得出事實的人才寫得出來的，不寫進概述，也不要為此多問一輪。〈待確認〉同樣不必追問——要需求方拍板的事多半在評估之後才浮現。
- **必填到齊就停筆**。單子開得快比寫得漂亮重要。
- 對方答「不知道」就照實寫「未確認」，不要替他猜；當下就知道要需求方拍板的事，寫進〈待確認〉。

## 各章節怎麼寫

### 現況與問題

先講現況，再講為什麼要改。**理由要寫**——調整單常常在半年後被翻出來問「當初為什麼改成這樣」，那句理由就是答案。理由可以是安全性、法規、使用者回饋、營運需求，但不能是「PM 說要改」。

兩三句就夠，不必鋪陳。

### 調整內容

這是整張單最重要的一段。要讓接手的人**不必猜**：

- **指名到位**：畫面上的位置、設定項名稱、欄位名，逐項寫出來，不要只寫「相關設定」。開單的人若知道檔案路徑與設定鍵名就一併寫上；不知道也沒關係，那是 RD 查得出來的，但「動到哪裡、改成什麼」一定要講清楚。同一個異動散在三個地方，就把三個都列出來。
- **給前後對照**：值的異動一律寫「調整前 → 調整後」，或用兩行分列。只寫「改成 https」會讓人不確定其餘部分（主機、路徑、參數）要不要跟著動；明講「其餘不變」就沒有這個疑慮。

```markdown
`config/notify.json` 的 `SmsEndpoint`，通訊協定由 `http` 改為 `https`
（主機、路徑與參數不變）：

調整前：`http://sms.example.com/api/send?...`
調整後：`https://sms.example.com/api/send?...`
```

- **不夾帶順手改的東西**。看到旁邊有別的問題想一起處理，開另一張單。混在一起的調整單無法單獨回滾，也無法單獨驗收。

### 驗收標準

每一條都要能**做一次就判定通過或不通過**：誰做什麼動作，會看到什麼結果。不要寫「測試功能正常」——那種句子在驗收會議上只會變成各說各話。

```markdown
- 於後台觸發簡訊發送，收件者確實收到簡訊，且發送紀錄的端點顯示為 https
- 既有的排程簡訊照常發送，內容與異動前相同
- 端點暫時無法連線時，顯示錯誤訊息且不重複扣款
```

補充兩點，寫得出來就一併列進條目：

- **回歸確認**：原本就有的行為沒被弄壞——你知道有哪些連帶對象就一併點名。
- **多環境**：涉及環境別的設定異動，逐個環境列出來——只在測試站確認過就上正式站，是這類單子最典型的翻車方式。

## 語氣與用字

- 全篇繁體中文；設定鍵名、路徑、欄位名、程式碼維持原樣不翻譯。
- 描述事實，不評價人。寫「目前設定為 `http`」，不寫「當初怎麼會用 `http`」。單子會被很多人看到，包含原作者。
- 具體值優先於形容詞：寫「由 6 碼提高為 12 碼」而不是「提高安全性」。
- 半形括號留給程式碼，全形括號留給中文。

## 送出

標題進 Redmine 的「主題」欄位，上面那份骨架**整份**進「概述」欄位。不要把章節拆散塞進自訂欄位，也不要拿這份骨架去寫註記；註記只寫這次新增的事實。

追蹤標籤選「調整」，專案取問題所在系統對應的專案。

追蹤標籤與專案在單子上是 id，不是名稱：透過 API 或工具開單時要先查**該站**的清單，把名稱對成那個站的 id。各站的 id 體系彼此獨立，不要憑記憶填數字，也不要沿用別站查到的 id。

預計完成日（`due_date`）由需求方或 PM 決定，透過工具開單時是必填欄位：不知道就在對話裡問，給選項讓對方選（例如「這週內／這個月底／沒有特定期限」），**不要自行推定一個日期**——推定出來的日期會被下游當成需求方答應過的期限。

影響範圍不放這裡。查得出事實的人依 `references/change_request/assess.md` 的評估註記模板撰寫，內容追加為註記，不要覆寫概述；查出來的驗收判準與待確認則相反，一律回頭補進概述。

怎麼交付依你手上有什麼：能直接寫進 Redmine 就照上面的落點寫，寫完把單號與網址回報給使用者；不能就把標題與內文分成兩塊輸出在對話裡，讓使用者自己貼。兩種都一樣，送出前先讓使用者確認——開單是對外動作，不要自作主張。
