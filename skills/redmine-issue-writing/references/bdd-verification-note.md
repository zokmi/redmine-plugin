# BDD 驗證後續註記

更新前必須先取得一致性審核子代理的 `PASS`。審核代理應使用當下動態選出的適用 skill，讀取 issue 完整需求、git 變更與 BDD 證據；不得修改檔案或寫入 Redmine。

## 驗證截圖上傳前審查

提供或上傳驗證截圖前，須由唯讀子代理統一審查整批最終圖片與預計發布的逐條說明。可由一致性審核子代理一併執行，但須另列圖片審查結論。主流程提供完整需求、驗收條目、修正項目、BDD 結果、圖片實際路徑與對應說明。

子代理必須使用圖片檢視工具實際開啟每張圖片，不得只憑檔名、OCR、測試通過或主代理摘要判定，逐條檢查：

1. 圖片可讀、文字清楚、關鍵畫面完整，沒有錯誤頁、載入中或遮擋驗證內容。
2. 畫面中的操作、資料、狀態與結果足以支持對應條列說明；前後差異與操作流程須有足夠證據，不由靜態畫面推定未呈現的行為。
3. 每個修正／驗收條目都有對應圖片，編號、檔名與說明一致；同圖支援多項時須逐項指出可見依據。
4. 以測試紀錄確認圖片來自本次驗證版本與情境，不猜測來源。最終遮罩後仍能辨認驗證結果，且無帳密、token 或不應公開的個資。

審查報告固定輸出「條目編號｜圖片路徑／檔名｜實際可見依據｜PASS／FAIL／UNVERIFIED｜缺漏與補驗方式」，最後給整批結論。圖片打不開、未實際看圖或證據不足為 `UNVERIFIED`；無法啟動子代理或使用圖片檢視工具為 `UNAVAILABLE`。只有全部適用條目 `PASS` 才可提供驗證截圖或呼叫 upload_attachment；其他結論均停止圖片交付與上傳，保留本機證據並回報缺口。

主流程補驗、重截或調整說明後交子代理複審。圖片經裁切、遮罩、替換，或對應說明、程式版本、驗證情境改變後，受影響條目必須重審，不得沿用舊 PASS。發現產品或測試異常時，依 systematic-debugging 先重現、蒐證與查明根因，再修正及重新驗證。

純 API／DB 條目標記「截圖不適用」，以可重現的請求／回應或查詢結果逐條審查；不得豁免需要 UI 證據的條目。此關卡適用驗證證據，使用者提供的原始問題截圖不得當作修正通過的證明。

只有一致性與圖片審核均通過、BDD 全部通過、截圖已遮罩且附件／註記儲存結果已確認，才能追加以下 PM 版格式：

```markdown
## 修正結果

### 修正項目 1：<修正項目名稱>

結果：已修正

圖片 1：<已上傳附件名稱或連結>

### 修正項目 2：<修正項目名稱>

結果：已修正

圖片 2：<已上傳附件名稱或連結>
```

PM 註記只呈現修正結果與畫面證據；根因、Scenario、commit、檔案行號與一致性審核細節保留在 BDD 報告及查核報告。每個修正項目都要有同編號的圖片。若是純 API／DB 情境，不能捏造圖片，改寫成：

```markdown
圖片 1：截圖不適用；請求／回應或查詢證據：<報告路徑、附件或可重現指令>
```

附件上傳或註記儲存未確認時，回報部分完成並停止後續結案，不得宣稱 Redmine 已更新完成。
