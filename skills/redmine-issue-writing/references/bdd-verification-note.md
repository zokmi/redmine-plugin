# BDD 驗證完成模板

BDD 階段回寫與最終回寫預設都使用下列附圖格式。只有使用者明確要求「精簡」時，才改用每項一句的文字條列。精簡回覆仍須交代驗證範圍、實測結果、未驗與待確認項目。階段註記只就該階段已驗的範圍下結論。

更新前必須先取得一致性審核子代理的 `PASS`。審核代理應使用當下動態選出的適用 skill，讀取 issue 完整需求、git 變更與 BDD 證據；不得修改檔案或寫入 Redmine。

```markdown
## 修正結果

受測版本：<分支>（程式 <短 SHA>），<環境> BDD 實測 <N> 個情境<全數通過／X 過 Y 失敗>；依<需求來源：概述原文、規則補充註記 #<編號> 或本批回饋>逐條回覆。未附圖的部分以<資料庫查詢／API 回應／單元測試>驗證。

### 修正項目 1：<對應驗收標準的條文，保留原條號或原文用語>

結果：<已修正／已確認維持／部分驗證／未通過>。<逐一寫出本版觀察到的操作、畫面文字、狀態或數值。未附圖的子項寫明依據，例如「以 API 回應驗證，未附圖」>

圖片 1：<圖中可見的值或狀態，一句話>

<upload_attachment 回傳的 markdown 原樣>

### 修正項目 2：<對應驗收標準的條文>

結果：<判定>。<本版實際觀察到的結果>

圖片 2：截圖不適用；<實際回應或查詢值，例如 HTTP 狀態碼與回覆訊息>，證據保存於本機 BDD 紀錄。

### 其他資訊補充

- 未驗證：<項目>；<原因與目前依據，例如依程式判斷／僅單元測試>
- 待確認：<需求方需決定的延伸行為>，請確認是否符合預期
- 圖片說明：<圖片編號、畫面看不出的前置狀態差異與各自的佐證來源>
- 上線注意：<同版上線、SQL 腳本、設定或部署順序>
```

- 前言寫明本批或整單的需求來源與實測數字。有阻塞、待驗或未執行時另列數量，未附圖的驗證方式依實際證據填寫，全數附圖可省略該句。
- 驗收標準逐條回覆只放驗收結果。除前言的受測版本短 SHA 外，根因、情境代號（Scenario）、commit 清單、檔案行號與測試過程留在本機 BDD 報告。
- 依需求條文順序編號，一條驗收標準對應一個修正項目。新增回饋用註記與可辨識的條文定位。同條有多個操作或結果時逐一交代。
- 結果判定只用「已修正」、「已確認維持」、「部分驗證」、「未通過」。整條未驗只列在「其他資訊補充」並保留條文定位。已驗子項皆符合、仍有子項未驗時寫「部分驗證」。已有子項實測失敗時寫「未通過」並點名失敗項。兩種情況都在補充列出尚未驗證的子項與原因。
- 圖片在整則註記中連號，一個修正項目可有多張圖。同圖證明多條時只上傳一次，後續條目以「同圖片 N」引用並說明該圖的可見依據。檔名建議使用 `<單號>-<序號>_<情境代號>_<簡述>.png`。
- 新圖以 `upload_attachment` 上傳，將回傳的完整 `markdown` 原樣貼在圖片說明下方。它已含圖片內嵌語法。將每張圖的 `token` 與回傳的 `filename` 配對帶入同次寫入的 `uploads`。回讀已刊登註記，確認內嵌圖片顯示且引用對應正確。附件或註記儲存未確認時回報缺項，保留本機證據並停止結案。
- 「其他資訊補充」只列有內容的子項。四項皆空仍保留標題，內文寫「無」。外觀相同而前置狀態不同的圖片，第一次回寫就要在「圖片說明」逐張交代差異與佐證來源，不留待事後另發註記。

## 驗證截圖上傳前審查

提供或上傳驗證截圖前，須由唯讀子代理統一審查整批最終圖片與預計發布的逐條說明。可由一致性審核子代理一併執行，但須另列圖片審查結論。主流程提供完整需求、驗收條目、修正項目、BDD 結果、圖片實際路徑與對應說明。

子代理必須使用圖片檢視工具實際開啟每張圖片，不得只憑檔名、OCR、測試通過或主代理摘要判定，逐條檢查：

1. 圖片可讀、文字清楚、關鍵畫面完整，沒有錯誤頁、載入中或遮擋驗證內容。
2. 畫面中的操作、資料、狀態與結果足以支持對應條列說明；前後差異與操作流程須有足夠證據，不由靜態畫面推定未呈現的行為。
3. 每個已驗且需要畫面佐證的條目都有對應圖片，編號、檔名與說明一致；同圖支援多項時須逐項指出可見依據。
4. 以測試紀錄確認驗證結果的圖片來自本次受測版本與情境。引用修正前圖片時，核對原始回報或舊版重現來源。最終遮罩後仍能辨認驗證結果，且無帳密、token 或不應公開的個資。

審查報告固定輸出「條目編號｜圖片路徑／檔名｜實際可見依據｜PASS／FAIL／UNVERIFIED｜缺漏與補驗方式」，最後給整批結論。圖片打不開、未實際看圖或證據不足為 `UNVERIFIED`；無法啟動子代理或使用圖片檢視工具為 `UNAVAILABLE`。只有全部適用條目 `PASS` 才可提供驗證截圖或呼叫 upload_attachment；其他結論均停止圖片交付與上傳，保留本機證據並回報缺口。

主流程補驗、重截或調整說明後交子代理複審。圖片經裁切、遮罩、替換，或對應說明、程式版本、驗證情境改變後，受影響條目必須重審，不得沿用舊 PASS。發現產品或測試異常時，依 systematic-debugging 先重現、蒐證與查明根因，再修正及重新驗證。

純 API／DB 條目標記「截圖不適用」，以可重現的請求／回應或查詢結果逐條審查；不得豁免需要 UI 證據的條目。此關卡適用驗證證據，使用者提供的原始問題截圖不得當作修正通過的證明。
