# Redmine 新需求單：DB 子單概述的資料表與關聯章節

新需求的資料表資訊只承載一件事：**這個需求會碰到哪些資料表、它們怎麼串起來。**

這兩章寫在 **DB 子單的概述（`description`）**，不是註記。DB 這一層已經有自己的子單，資料表的事全部落在那張單上；同一份內容在別處再放一份，兩處遲早不同步，而讀的人不知道哪一份算數。DB 子單怎麼開、〈結構異動〉與資料表關聯圖怎麼寫，見 `references/feature_request/feature.md` 的〈新功能開發要拆子單〉與〈DB 子單的資料表關聯圖〉。

其餘的東西——需求怎麼改、範圍縮到哪、相依查到什麼、哪個判準拍板了——**一律回頭更新母單的概述**。概述是那張單目前最新的樣子，過程資訊散在十則註記裡等於沒有人知道現在的需求是什麼。母單概述的寫法見 `references/feature_request/feature.md`。

這兩章是給接手實作與日後維護的人看的：**看完就知道資料落在哪裡，不用自己從頭翻一遍。**

## 下筆前：先把事實釘死

這兩章的每一項都會被下游當成有人查過。因此下筆前先問自己一句：
**這件事我是查到的，還是推出來的？**

算事實的：翻過資料表定義、讀過原始碼裡的查詢與寫入、實際查過資料內容。
不算事實的：「這張表看名字應該是存訂單的」「這兩張表通常會用 `Id` 對」。

推出來的東西只有兩條路——去查證，或整項不寫。**不要折衷寫成「可能會影響」**：
那句話會讓讀的人以為有人看過了，於是他也不查，比留白更糟。

## 排版格式

同新需求單概述：一律 Markdown，章節用 `##`，資料表名、欄位名、型別、狀態值用反引號，條列用 `-`。不要用 textile，不要用連字號分隔線。

資料表關聯要用條列或表格寫出欄位對欄位——那是權威的一份。DB 子單另外要畫一張純文字概觀圖（畫法見 `references/feature_request/feature.md` 的〈DB 子單的資料表關聯圖〉），但圖不取代條列。

## 內文骨架

兩章都是「有事實才寫」。沒有就整段拿掉，不要留空標題。

````markdown
## 涉及的資料表

<每張表：用途一句話 + 這次會用到的關鍵欄位>

## 資料表關聯

<哪張表用哪個欄位對到哪張表、一對多還是一對一、有沒有軟刪除或狀態欄要一起帶>
````

## 查到之後要回頭更新概述

**要新增或修改的表與欄位寫在同一張 DB 子單的〈結構異動〉那一章**（名稱、型別、可否為空、預設值、既有資料怎麼補），格式見 `references/feature_request/feature.md`。它在開發過程還會被改一兩輪，所以要留在改得動的概述裡，永遠只有一份。

資料表在開發過程改了，這兩章與關聯圖也一起回頭改掉，不要另外追加一份新的。

需求面的異動（範圍、判準、相依、待確認）屬於母單：**回頭更新母單的概述**，不要留在 DB 子單裡。概述改動幅度大時，可以追加一則一兩句話的註記說「概述已更新：⋯⋯」，讓關注者知道要重讀；但需求本身仍然只有概述那一份。

- [ ] 需求面的異動（範圍、判準、相依、待確認）已更新回母單概述
- [ ] 每一項都講得出「我從哪裡查到的」，沒有「應該／可能／通常」這類推測句
- [ ] 資料表名與欄位名照抄實際名稱，沒有憑印象改大小寫或補底線

## 各章節怎麼寫

### 涉及的資料表

每張表一行用途，再列這次真的會用到的欄位。**不要把整張表的欄位抄一遍**——抄全部等於沒有標重點，讀的人還是得自己判斷。

```markdown
- `TblOrder`：訂單主檔。用到 `OrderId`、`MemberId`、`OrderStatus`、`CreateTime`
- `TblOrderDetail`：訂單明細，一張訂單多筆。用到 `OrderId`、`ProductId`、`Qty`
- `TblMember`：會員主檔，只讀不寫。用到 `MemberId`、`MemberName`
```

只讀、會寫、會刪要標出來。只讀的表通常不用進回歸測試，會寫的表要。

### 資料表關聯

寫清楚**用哪個欄位對哪個欄位**，以及**一對一還是一對多**。這兩件事漏掉，接手的人第一個查詢就會寫錯。

```markdown
- `TblOrder.OrderId` 1 : n `TblOrderDetail.OrderId`
- `TblOrder.MemberId` n : 1 `TblMember.MemberId`
- `TblOrderDetail` 沒有實體外鍵，關聯只靠程式維護
- `TblOrder` 以 `IsDeleted = 0` 過濾，查詢時要一併帶上
```

**軟刪除欄位、狀態欄、租戶／站台欄這類「不帶就會撈到不該撈的資料」的條件要寫出來**。它們不是關聯，但漏掉的後果和關聯寫錯一樣嚴重。

沒有實體外鍵、或關聯只由程式維護時要講明白，否則讀的人會以為資料庫幫他擋住了。

## 語氣與用字

- 全篇繁體中文；資料表名、欄位名、型別、狀態值、路徑維持原樣不翻譯。
- 描述事實，不評價人。單子會被很多人看到，包含原作者。
- 具體優先於形容詞：寫「一張訂單最多 200 筆明細」而不是「明細不會太多」。
- 半形括號留給程式碼，全形括號留給中文。

## 送出

上面那兩章併進 **DB 子單的概述**，與該子單的〈需求內容〉〈結構異動〉〈驗收標準〉同在一份內文裡。

- **需求本身的異動不寫這裡。** 回頭編輯母單概述，把它改成最新狀態。
- **查不到就不要寫。** 空標題與「可能會影響」比留白更糟。
- 標題需要修正時只改「主題」欄位。

怎麼交付依你手上有什麼：能直接寫進 Redmine 就照上面的落點寫；不能就把內容輸出在對話裡，讓使用者自己貼。兩種都一樣，送出前先讓使用者確認。
