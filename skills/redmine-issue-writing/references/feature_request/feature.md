# Redmine 新需求單格式

依 SKILL.md 的共用落點、提問、寫入與交付規則。以下骨架與檢核已含必要規範；只有需要寫法範例時讀同目錄 `feature-details.md`，不要預設載入。

## 主題與母子單

主題：`<誰／哪個模組>：<新增什麼能力>`，動詞具體。
母單寫使用者可見行為與跨層驗收，三張子單各自寫層內驗收；母單需求內容列出子單單號。
子單主題：`<一致的功能名>（UI／API／DB）：<這層要做什麼>`。
再拆的單掛該層子單；不動的層照開，寫原因並結單。

- UI：進入點、畫面位置、欄位限制與預設值、載入／無資料／錯誤／權限狀態、可見性、文案原文。
- API：端點方法與分頁、輸入輸出欄位型別與必填、驗證錯誤、角色權限、筆數與效能上限。
- DB：先讀 `assess.md` 的資料表與關聯格式；列結構與索引（名稱、欄位、服務查詢）、既有資料回填；用中文描述，不貼 SQL 條件、DDL 或系統預存程序。
- DB 純文字關聯圖：標一對多方向、新增表欄位、軟刪除／狀態／租戶過濾、無實體外鍵處；圖下仍列欄位對欄位關聯。

## 骨架

前三章必填；後四章只寫已查證或定案事實，無內容刪掉。母單不放結構異動，該章只在 DB 子單。
需求描述做什麼與邊界；驗收涵蓋正常、無資料、超上限與權限不足，可一次判定。
待確認定案後將結論更新需求／驗收，刪除已答項目；範圍排除不重列成驗收。

````markdown
## 背景與目的

<誰、在什麼情境下、遇到什麼不便；做了這件事之後會變成怎樣>

## 需求內容

<要新增的能力：進入點、操作流程、資料範圍、規則>

## 驗收標準

<可驗證的條列：誰做什麼動作，會看到什麼結果>

## 影響範圍與相依

<會動到哪些既有功能、需要哪些前置條件或外部資源>

## 結構異動

新增或修改的每一張表各一段：表名一句用途，接一張逐欄位的表格。

**<資料表名>**：<這張表裝什麼，一句話>

| 欄位 | 型別 | 可否為空 | 預設值 | 中文說明 |
|---|---|---|---|---|
| `<欄位名>` | `<型別>` | not null／null | `<預設值>`／無 | <這個欄位裝什麼、值域或對到哪張表> |

<既有資料怎麼補：留空、回填預設值，還是要跑一次資料轉換>

## 不在範圍內

<明確排除、這次不做的事>

## 待確認

<需要需求方拍板才能定案的部分>
````

## 自我檢查

送出前逐項確認；每一項的展開說明在下面各節：

- [ ] 骨架整份寫在概述（`description`）欄位，沒有拆散到其他欄位
- [ ] 追蹤標籤與專案填的是查該站清單換到的 id，預計完成日是問出來的、不是自行推定的
- [ ] 標題兩段齊全（誰／哪個模組、新增什麼能力），動詞具體
- [ ] 內文是 Markdown：章節用 `##`，欄位名用反引號，沒有 textile 語法或連字號分隔線
- [ ] 背景寫的是可判斷的結果，不是「提升效率」這類形容詞
- [ ] 需求內容描述「要做什麼」而非「怎麼實作」，且涵蓋規則與邊界
- [ ] 每條驗收標準都能一次判定通過或不通過
- [ ] 錯誤與邊界情境（無資料、超上限、權限不足）都有對應條目
- [ ] 後四章寫的都是查到或討論定案的事實，沒有「應該／可能／通常」這類推測句
- [ ] 這次討論改到的需求已經更新回概述，不是只留在註記或對話裡
- [ ] 新功能開發已拆成母單＋UI／API／DB 三張子單，三張都建了，且各自掛在正確的父任務底下
- [ ] 母單只留跨層驗收條目，沒有重述各層細節；各層子單都有自己的驗收標準
- [ ] 這次不動的那一層仍開了子單，並寫明本次不動及原因
- [ ] 有結構異動時，〈結構異動〉是逐欄位的表格，五欄（欄位、型別、可否為空、預設值、中文說明）都填了，中文說明不是重述欄位名
- [ ] DB 有資料或結構變動時，子單的概述有純文字資料表關聯圖，標了一對多方向、新增的表與欄位、必帶的過濾條件與無外鍵之處
- [ ] DB 子單全篇以中文敘述描述結構，沒有 SQL 條件式、DDL 或系統預存程序（讀者含非 IT，且部分站台的 WAF 會攔）
- [ ] 需要關聯圖時，下方仍有欄位對欄位的條列，不是只有圖
- [ ] 不確定的地方標了「未確認」，沒有留白
- [ ] 必填內容都來自需求方提供，缺的部分是問出來的，不是你補的猜測
- [ ] 沒有空章節，也沒有為了填滿而猜的內容
