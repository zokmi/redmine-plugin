# Redmine 臭蟲單文案格式

一張好的臭蟲單要讓三種人各取所需：**PM 看得懂影響**、**接手的 RD 不必重查一遍就能動手**、**未來的人回頭翻單時知道當初為什麼這樣修**。以下格式就是為這三件事服務的——每個章節都有它要回答的問題，沒有那個問題就不要硬寫那個章節。

## 下筆前：先把事實釘死

臭蟲單的價值來自**可驗證**。單子裡出現的每個檔案路徑、行號、程式碼片段、列舉值，都必須是你真的讀過原始碼確認的，不能憑印象或從對話上文複製。行號寫錯會讓接手的人在錯的地方繞半天，比不寫更糟。

動筆前確認：

- 缺陷位置：檔案路徑（從 repo 根開始）＋行號，並實際讀過該段原始碼確認
- 觸發條件：什麼操作、什麼前置狀態才會踩到
- 影響面：誰會遇到、多常遇到、有沒有資料被破壞、可否自行復原
- 根因：不是「這行寫錯了」，而是「為什麼會寫成這樣」——是判斷放錯區塊、語意誤用、還是兩套概念被混淆
- 相關聯的地方：同樣寫法有沒有擴散到別處、有沒有測試把錯誤行為固化了

最後一項最容易漏，卻常是單子裡最有價值的部分。單點修好但同源問題還在別處，等於沒修。

## 標題

```
<受影響的對象>：<技術根因>，<使用者可見後果>
```

冒號前指出壞掉的東西（必要時用括號附上欄位／變數名，讓人能直接搜），冒號後左半是機制、右半是使用者實際會遭遇的事。三段齊全，PM 和 RD 各自都能從標題判斷要不要點進來。

**範例：**

- `填寫步驟(cStepDone)狀態還原錯誤：EditRecord 無條件以 cProgress 覆寫，使用者被拉回步驟2`
- `匯出報表金額短少：SumAmount 未含稅額欄位，財務對帳每筆差 5%`

反例：`cStepDone 有 bug`（沒有機制、沒有後果，等於逼人整份讀完才知道嚴不嚴重）。

## 排版格式

單子內文一律用 **Markdown**，不要用 textile。`h3. 標題` 這類 textile 語法在 Markdown 站台會原樣顯示成純文字，反而更難讀。

- 章節標題用 `##`，章節內的子標題用 `###`；靠標題階層分段，不要用連字號分隔線。
- 程式碼、原始碼片段、錯誤訊息一律用三個反引號的圍欄區塊，不要用四個空白縮排。
- 條列用 `-`，有先後順序才用 `1.`。
- 需要強調的欄位名或關鍵字用 `**粗體**`，但一段裡不要超過一兩處。

## 內文骨架

這份骨架是**註記**的內容，不是概述的內容——概述留給非 IT 人員看的現象描述，診斷往下追加在註記裡。詳見下方「送出」。

註記只寫**概述沒有的東西**。現象、操作步驟、預期與實際結果、驗收標準都已經在概述裡，再寫一遍只會讓讀者不知道該信哪一份、也讓兩份遲早不同步。註記要補的是三件事：機制（位置與程式碼）、概述看不出來的觸發條件、修正方向與判準。

診斷還會查出兩類**不屬於註記**的東西——概述漏掉的驗收判準、需求方要拍板的事——那兩類回頭寫進概述，見下方〈診斷後要回頭更新概述〉。

完整骨架如下，**依實際情況取捨**——只有一個缺陷就不必編號成「問題 1」；沒有需求面的疑問就整段拿掉「待確認」。空章節比沒有章節更浪費讀者時間。

````markdown
## 問題摘要

<領域概念澄清：把這張單會反覆提到的欄位／狀態／列舉，一次講清楚值域與語意>

<一句話點出衝突的核心>

## 問題 1：<一句話標題>（主要問題）

位置：<檔案路徑> 第 N 行

```csharp
<原始碼片段>
<出問題的那行>   // ← <為什麼這行有問題>
```

<散文一段：說明為何這樣寫是錯的>

觸發條件：<概述看不出來的前置狀態，含具體欄位值與列舉值；操作步驟已在概述，不重述>

## 問題 2：<...>

## 影響更正（選填）

<只在診斷結果與概述的描述不同時才寫：真正的觸發範圍、資料受損程度、能否自行復原>

## 建議修正

1. <修正方向>
   - <理由／判準>
2. <...>

## 參考

<同源問題、前例單號、相關文件；並註明哪些細節不可直接照搬>
````

## 自我檢查

交件前逐項確認；每一項的展開說明在下面各節：

- [ ] 註記只寫機制、觸發條件、修正方向與參考，沒有夾帶該回寫概述的內容
- [ ] 標題三段齊全（對象、機制、後果），能被搜尋到關鍵欄位名
- [ ] 內文是 Markdown：章節用 `##`／`###`，程式碼用圍欄區塊，沒有 textile 語法或連字號分隔線
- [ ] 每個檔案路徑與行號都實際讀過原始碼確認，不是憑印象
- [ ] 沒有重述概述已有的現象、操作步驟與預期／實際結果
- [ ] 觸發條件帶具體欄位值與列舉值，是概述看不出來的那一段
- [ ] 影響只在診斷結果與概述不同時才寫，且誠實，沒有誇大也沒有輕描淡寫
- [ ] 檢查過同樣寫法是否擴散到別處、是否有測試固化了錯誤行為
- [ ] 建議修正給的是方向與判準，不是整段實作
- [ ] 診斷才看得出來的驗收判準已補進**概述**的〈驗收標準〉，每條都能一次判定通過或不通過
- [ ] 需要需求方拍板的事已寫進**概述**的〈待確認〉，沒有藏在註記的敘述裡
- [ ] 概述改動幅度大時，註記有一句話說明概述改了什麼
- [ ] 沒有空章節

## 診斷後要回頭更新概述

驗收的人只看概述。判準若是「概述一份、註記一份」，他不會知道還有第二份要讀；需求面待拍板的事留在註記，也會被後續一則又一則的留言蓋過去。因此診斷查出來的這兩類內容**回頭寫進概述**，不放註記：

| 查出來的東西 | 寫進概述哪一章 |
|---|---|
| 概述漏掉的驗收判準 | 〈驗收標準〉，接在原有條目之後 |
| 要需求方拍板才能定案的事 | 〈待確認〉；概述沒有這一章就新增在最後 |

- **直接改，不必保留沿革**。Redmine 自己有編輯歷程，「原本是⋯⋯後來改成⋯⋯」只會讓概述愈讀愈長。
- **不要動回報者寫的現象、重現步驟與既有判準**。你是追加與更正，不是重寫——概述仍然是非 IT 讀者的入口。診斷結果與概述描述不符時，寫進註記的〈影響更正〉，那是紀錄「原本說的不對」，不是覆寫。
- **概述改動幅度大時，在註記寫一句「概述已更新：⋯⋯」**，讓關注這張單的人知道要重讀。

### 補進概述的驗收標準

概述已經有一份驗收標準了，這裡**只追加它列不出來的判準**——那些要讀過原始碼才知道要驗的東西。每條同樣要能做一次就判定通過或不通過。

```markdown
- 既有已被寫壞的資料（cStepDone < cProgress）經修復程序後恢復一致
- EditRecord 與 ImportRecord 兩處行為一致（同源問題已一併處理）
- 新增單元測試涵蓋上述分支，且原本以錯誤列舉值斷言的測試已改正
```

這三類是診斷才看得出來的：**既有壞資料要不要一併修、同源問題有沒有一併處理、被錯誤行為固化的測試有沒有改掉**，不列進驗收就會被漏掉。反過來說「於步驟3 編輯後儲存，畫面停在步驟3」這種概述本來就寫得出來的條目，不要再抄一次。

與註記〈建議修正〉的分工是：建議修正給方向，驗收標準給判準——改法可以換，判準不能少。

### 寫進概述的待確認

技術上能修、但**要不要這樣修得由需求方決定**的部分寫進概述的〈待確認〉。把選項與影響範圍講清楚，明確提問，別把疑問藏在註記的建議修正裡讓人自行體會。

若別的專案有同類需求可作為對照，一併說明兩者涵蓋範圍差在哪，最後給一句判斷：「若需要，缺的是整套機制而非單一修正。」——讓 PM 知道這不是順手加的小改動。

## 各章節怎麼寫

### 問題摘要

先做**領域概念澄清**再談問題。多數難纏的 bug 起因於兩個概念被混為一談，讀者若不先分清這兩者，後面所有推論都跟不上。用條列把每個概念的值域與語意攤開：

```
- cProgress（申辦進度）：0 尚未開始 / 1 已閱讀說明 / 2 填寫完成 / 3 送審完成
- cStepDone（前台填寫頁內層步驟，已完成的步驟數）：0=停在步驟1 注意事項 … 4=停在步驟5 資料確認
```

然後一句話收束：「兩者值域與語意都不同，不可互相賦值。」

如果這張單不牽涉概念混淆，**整節拿掉**。「哪個功能在什麼情況下產生什麼錯誤結果」概述已經寫過，重述一遍沒有增加任何資訊。

### 問題 N

一張單常常會挖出不只一個問題。**依嚴重度排序**，最主要的那個標註「（主要問題）」，讓人知道從哪裡開始看。

- **位置**永遠獨立一行，格式 `位置：<路徑> 第 N 行`（區段則寫 `第 N-M 行`），方便被搜尋與複製。
- **程式碼片段**只貼最小可理解範圍，通常 3–5 行，放在圍欄區塊內並標上語言。用該語言的註解符號加 `← ` 在出問題那行右側標註要害，這比在下方另起一段解釋更快進入狀況。
- **觸發條件**只寫概述看不出來的那一段——踩中缺陷所需的前置狀態，帶具體數值，不要寫「某個狀態」。寫 `cStepDone = 5、cProgress = 1 已閱讀說明` 別人才照著做得出來；列舉值同時給數字與中文名，兩邊的人都讀得懂。操作步驟概述已經有了，不要重打一份；只有在概述的步驟其實重現不出來時，才另寫一份正確的並說明差在哪。
- **影響更正**只在診斷推翻概述的判斷時才寫——例如觸發面比回報者以為的更廣（不只他那個帳號）、或資料其實可以自行復原（「填寫結果本身不會遺失，使用者重新往前走可恢復；但需重走已完成的步驟，體驗與信任受損」）。診斷結果與概述一致就整節拿掉，也記得回頭調整單子的「優先權」欄位而不是在內文加一段文字。

**特別值得寫成獨立一則的兩種情況：**

1. **同樣的錯誤寫法已擴散到別處**——尤其當程式碼裡有「比照 XXX」之類的註解，代表錯誤語意已被當成慣例。這種要點名，否則修完一處問題仍在。
2. **測試把錯誤行為固化了**——例如以錯誤的列舉型別去斷言欄位。這種測試日後會「綠著騙人」，必須連同測試一起列為待修，並在「建議修正」給出正確斷言方式。

如果目前的執行結果**碰巧正確**（兩套數值恰好重疊），要明講「這是巧合而非設計意圖，任一列舉值調整就會出錯」。這類潛伏問題不寫下來，就永遠沒人會修。

### 建議修正

給方向與判準，不要貼整段實作。接手的人需要的是「為什麼要這樣改」，實作細節他自己會依現場情況決定；貼死的程式碼反而會綁住他。

依「先抽共用、再改各呼叫點、最後補測試」的順序編號，每項底下用子條列補上判準與理由：

```markdown
1. 抽出共用的純函式判斷「是否需要還原步驟、還原到哪一步」，兩處共用，避免規則分歧。
   - 還原目標固定為 cStepDone = 1（停在步驟2）。注意事項的閱讀同意不受後續資料異動影響。
   - 判準建議以「該筆有無填寫資料」而非 cStepDone 現值：現值可能已被本問題寫壞。
2. RecordService.cs:1735 該行移入 if (record.CProgress != args.CProgress) 區塊內。
```

注意最後一項的寫法——**當某個欄位的現值本身就是本 bug 的受害者，就不能拿它當判斷依據**。這種推論寫進單裡，能省下接手者踩第二次坑。涉及邏輯驗證的修正，記得把補上單元測試也列為其中一項。

### 參考

同源問題的既有修正、相關單號、規格文件。跨專案引用時**必須註明差異**，避免接手的人直接照搬：

```markdown
同源問題已於 A 專案修正，可參考其判準與規則（實作細節不可直接移植，因本專案
的填寫資料表為 TblRecordDetail、題目為三層結構，與 A 專案的扁平 TblFormItem 不同）：
- A 專案 #12341：解鎖還原誤將未啟用資料的進度推進
- A 專案 #12309：解鎖與編輯改依填寫資料判斷
```

## 語氣與用字

- **全篇繁體中文**；程式碼、識別字、路徑、欄位名維持原樣不翻譯。
- **描述事實，不評價人**。寫「這行不在 if 區塊內，代表每次編輯都會執行」，不寫「這裡寫得很爛」。單子會被很多人看到，包含原作者。
- **半形括號留給程式碼，全形括號留給中文**：`cProgress（申辦進度）`、`（主要問題）`。
- 中英數之間不強制加空格，跟隨既有單子的習慣即可。
- 列舉值一律**數字＋中文名並列**：`已閱讀說明(1)`、`cProgress = 1 已閱讀說明`。
- 避免「應該」「可能」這類軟化詞去描述你已經確認的事實；真的不確定的地方，就明說「未驗證」或放進「待確認」。

## 送出

**機制、修正方向與參考一律寫進註記，不寫進概述。** 概述是給非 IT 人員看的——現象、重現、驗收標準，就是回報階段那份骨架的範圍（急迫度走「優先權」欄位，不在內文）；診斷的技術內容屬於註記。

例外是上面〈診斷後要回頭更新概述〉列的兩類：查出來的驗收判準與需求面待確認，補進概述對應的章節。

**已經有單**：上面整份骨架進「新增註記」欄位，再依前述兩類內容補進概述。除此之外不要動概述——現象與重現步驟是回報者寫的，覆寫掉等於把非 IT 讀者的入口拿走。

**還沒有單**（RD 自己發現的問題）：分兩步。先依 `references/bug_report/report.md` 的回報階段格式寫出現象、重現與驗收標準開一張單，追蹤標籤選「臭蟲」，專案取當前 repo 對應的專案；再把診斷追加為註記。

標題不受此限。診斷出機制後把標題補成三段是應該的，那是只改「主題」欄位的事，不要順手動到概述。

怎麼交付依你手上有什麼：能直接寫進 Redmine 就照上面的落點寫，寫完把單號與網址回報給使用者；不能就把標題與內文分成兩塊輸出在對話裡，讓使用者自己貼。兩種都一樣，送出前先讓使用者確認——這是對外動作，不要自作主張。
