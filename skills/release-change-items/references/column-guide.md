# 版更項目七欄填寫準則

每欄的判斷標準與實例。核心心法：**這格的讀者是過版當下的 RD 與事後的複檢人員**，
他們沒有你現在的上下文。寫下去的東西要能讓他們在半夜停機時照著執行、照著核對。

## 1. Redmine編號

- 格式 `#4590`，保留井字號，與 commit 標題慣例一致。
- 一張單一列。同一張單有多個 commit 就合併成一列，不要拆。
- 沒有單號的異動：寫「無單號」，備註列出 commit 短碼與標題，讓 PM 判斷要不要補單。
- `#0000` 是公司慣用的佔位號，不是真實單號，比照「無單號」處理。

## 2. 簡述

一句話，說明**這張單對正式環境造成什麼改變**，不是說明開發做了什麼。

- 好：`日週報主委/專案候選為空時回退為文字輸入框`
- 好：`Report9 坪數分析改由後端聚合，前端不再自行計算`
- 差：`refactor report9`（讀者看不出影響）
- 差：`修正 bug`（等於沒寫）

Redmine 主旨可以當起點，但主旨常常太簡略（例如「串接 bpm 拋轉資料」）。
看過 git diff 後如果能講得更精確，就用你判讀出來的版本。

## 3. 異動SQL

這欄的用途是讓 RD 在停機時**照著執行**，所以要寫語句本身，不是檔名。

- 有 SQL 檔異動 → 打開檔案，摘出實際語句。長的話取關鍵那幾行加註來源檔名：
  ```
  ALTER TABLE tblCase ADD cIdCard NVARCHAR(20);
  （完整內容見 SQL/20260320_alter_tblCase_add_cIdCard.sql）
  ```
- 只有索引／效能調整也要寫，因為執行時間可能影響停機區間長度：
  ```
  CREATE INDEX ix_tblBuildCaseReportTag_cKey_cValue ON ...;
  ```
- 沒有 SQL 異動 → 寫「無」。空白會讓人分不清「不用執行」還是「還沒查」。
- 有資料修正（UPDATE／DELETE）→ 一定要在備註提醒先備份該表，並註明影響筆數如果查得到。
- EF Core Migration 也算 SQL 異動，寫出 migration 名稱與它產生的結構變更。

## 4. 異動設定檔(config、appsetting)

寫**鍵名與值**，不是檔名。過版人員需要知道要去正式機的哪個檔加哪一行。

```
appsettings.PROD.json：
"Bpm:Endpoint": "https://..."
"Bpm:ApiKey": "（向資安索取）"
```

判讀要點：

- 用 `git diff <range> -- <設定檔路徑>` 看實際改了哪些鍵，不要只列檔名。
- **正式環境的設定檔通常不在版控裡，或版控裡的值是假的。**
  看到 `appsettings.PROD.json` / `environment.prod.ts` 有異動，
  代表「正式機這個檔需要人工確認」，備註要寫明實際值要由誰提供。
- 敏感值（API key、連線字串、密碼）**不要抄進表格**。寫鍵名，值寫「（由 RD 於正式機設定）」
  或「（向資安索取）」。這份文件會流傳歸檔，不該帶著憑證跑。
- 前端 `environments/*.ts` 改 API base url 也算設定異動，因為部署後要確認打對後端。
- 沒有異動 → 寫「無」。

## 5. 異動程式

給複檢人員一個「這次動到哪些區塊」的地圖，不是完整檔案清單。

- 挑代表性的入口檔：Controller、Service、主要 component。
  `AuthController.cs / login.component.ts` 這種寫法就夠了。
- 檔案多時按專案分組，數量寫出來讓人有量感：
  ```
  webAPI：ReportService.cs / WeekReportTagHelper.cs 等 8 檔
  CRMAG：report8/report9 component 等 5 檔
  ```
- `doc` 桶（.md、docs/、openspec/）的檔案**不要填**。文件不影響正式環境行為，
  列進來只會讓複檢人員多花時間確認無關項目。
- `build` 桶（package.json、csproj）要不要填看情況：
  只有版號變動可略過；新增了套件相依就要寫，因為部署時要重新還原套件。
- 純前端異動記得標明，因為它決定 CDN 快取要不要清。

## 6. 影響之重大功能

只能從該份檢核文件「重大功能檢核清單」裡實際存在的功能模組挑選。
寫了清單裡沒有的名稱，複檢時找不到對應的 M 編號可以核，這格就白填了。

判斷方式用 `scripts/map_features.py` 把異動檔案對應到前台路由，共用檔與後端則用
`codegraph_explore` 回推呼叫端（詳見 SKILL.md 步驟 4）。

- 多個用頓號分隔：`登入、會員註冊`
- 判斷依據是「這次異動可能讓哪個既有功能壞掉」，不是「這次異動屬於哪個模組」。
  例如改了共用的驗證 helper，即使單子講的是報表，登入也可能受影響——要列。
- 真的沒有對應到任何重大功能（例如只改開發工具設定）→ 寫「無」，
  並在備註說明為什麼判斷無影響。這個判斷本身就是複檢人員要看的資訊。
- 這欄的內容必須與交付的「本次必檢清單」一致。同一份判讀出現兩種說法，
  過版當下沒人知道該信哪個。

## 7. 備註

放「過版當下需要知道，但前面六欄放不下」的事。典型內容：

- 執行順序限制：`SQL 需在 API 部署前執行，否則舊版程式會撞到新欄位約束`
- 待確認事項：`待確認：正式機 Bpm:ApiKey 由誰提供`
- 外部相依：`需與 BPM 端確認測試環境已同步開通`
- 回滾注意：`此 SQL 無法直接回滾，回滾前需還原 tblCase 備份`
- 無單號異動的來源：`commit 3e9a8636「標籤修正」、901db797「報表修正」，建議補單`
- git 與 Redmine 描述不一致時的說明

## 待確認的寫法

查不到、看不懂、或需要人來決定的，統一寫成「待確認：<具體要確認什麼>」。

不要寫模糊的「待確認」三個字——讀的人不知道要去確認什麼。
也不要為了讓表格看起來完整而編一個合理的猜測，過版文件裡的假資訊會直接變成漏檢。

## 完整範例（一列）

```
#4590	串接 BPM 拋轉資料，新增每日同步排程	無	appsettings.PROD.json："Bpm:Endpoint" / "Bpm:ApiKey"（值由 RD 於正式機設定）	webAPI/BpmSync：SyncService.cs 等 4 檔	無	待確認：Bpm:ApiKey 由誰提供；排程首次執行需人工觀察一輪
```
