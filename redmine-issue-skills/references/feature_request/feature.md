# Redmine 新需求單文案格式

新需求單處理的是**系統現在沒有、要新增的能力**。它與調整單的差別在於有沒有「現況」可以改：既有功能換個樣子是調整，從無到有是新需求。

一張好的新需求單只有一個判準：**驗收的時候，雙方不會對「這樣算不算做完」有歧見。**

做得到這件事的關鍵不是把需求寫長，而是把**驗收標準**寫清楚。

## 概述是活文件

新需求單的概述（`description`）是**這張單目前最新的樣子**，不是開單當下的快照。

需求在討論過程中被改了、範圍被縮了、相依查出來了、某個判準拍板了——**一律回頭更新概述**，把它改成最新狀態，不要把異動堆在一則又一則的註記裡。理由很簡單：驗收與開發的人只會看概述，過程資訊散在十則註記裡，等於沒有人知道現在的需求是什麼。

- 舊的寫法直接覆寫掉，不必保留「原本是⋯⋯後來改成⋯⋯」的沿革；Redmine 自己有編輯歷程。
- 改動幅度大時，可以另外追加一則一兩句話的註記說明「這次概述改了什麼」，讓關注者知道要重讀；但**需求本身仍然只有概述那一份**。
- **新需求單沒有註記落點。** 涉及的資料表與其關聯寫在 DB 子單的概述（格式見 `references/feature_request/assess.md`），結構異動也在那張子單的概述——它屬於需求的一部分，開發過程還會再改，得留在改得動的地方。

## 新功能開發要拆子單（母單＋UI／API／DB）

新需求若是**新功能開發**（要寫程式才做得出來的新能力），除母單之外一律再開三張子單：UI、API、DB。三張都要開，並在 Redmine 的「父任務」欄位填上母單單號。

**三張是下限，不是上限。** 工作量大時可以再往下拆（UI 分頁面、API 分端點），再拆出來的單掛在**該層子單**底下，不要平掛回母單——層級亂掉就看不出誰是誰的一部分。

**某一層這次不動也要開。** 例如完全不動資料表的需求，DB 子單照開，〈需求內容〉只寫一句「本次不動資料表：<原因>」，然後直接結掉那張單。這樣單數是固定的三張，回頭盤點時分得出「確認過不用做」與「忘了開」。

### 母單寫什麼

母單是需求全貌，維持〈概述是活文件〉那一節的規則。它**不重述各層細節**：

- 〈背景與目的〉與〈需求內容〉寫使用者看得到的行為，不寫欄位型別與端點。
- 〈驗收標準〉只留**跨層**條目——從畫面操作一路走到資料寫入、三層都上線才驗得過的那些。各層自己的判準寫在該層子單。
- 〈結構異動〉整段移到 DB 子單，母單不留——母單一份、子單一份，兩處遲早不同步。
- 〈不在範圍內〉與〈待確認〉留在母單，不要每張子單各寫一份。
- 子單開好後，在母單〈需求內容〉列出三張子單的單號，讓人一眼看到拆到哪裡。

### 子單主題格式

```
<功能>（UI）：<這層要做什麼>
<功能>（API）：<這層要做什麼>
<功能>（DB）：<這層要做什麼>
```

冒號前的功能名三張一致（與母單用同一個詞），列表上才會排在一起。

**範例：**

- `訂單明細批次匯出（UI）：訂單列表新增匯出按鈕與期間選擇`
- `訂單明細批次匯出（API）：新增匯出端點，回傳指定期間的明細`
- `訂單明細批次匯出（DB）：新增匯出紀錄表`

### 各層子單寫什麼

三張子單都套這份骨架（同樣的章節、同樣的自我檢查），差別在〈需求內容〉聚焦哪一層，而且**每張子單有自己的〈驗收標準〉**——那層做完了沒有，由該張單自己判定。

**UI 子單**必寫：

- 進入點與畫面位置（哪個選單、哪個畫面、按鈕放在哪）
- 欄位與輸入限制（必填、格式、長度、預設值）
- 狀態呈現：載入中、查無資料、錯誤、權限不足各顯示什麼
- 權限對可見性的影響（誰看得到、誰看不到）
- 畫面文案原文，用圍欄區塊貼上，不要轉述

**API 子單**必寫：

- 端點與方法，要不要分頁
- 輸入與輸出欄位（名稱、型別、必填與否）
- 驗證規則與錯誤回應（哪種情況回哪個狀態碼與訊息）
- 權限：哪些角色可呼叫，未授權時回什麼
- 筆數與效能上限（單次最多幾筆、逾時怎麼處理）

**DB 子單**必寫：

- 〈涉及的資料表〉與〈資料表關聯〉：這次會碰到哪些表、用哪個欄位對哪個欄位，寫法見 `references/feature_request/assess.md`
- 〈結構異動〉：要新增或修改的表與欄位，**逐欄位用表格列出**（欄位、型別、可否為空、預設值、中文說明），另加一句既有資料怎麼補
- 索引：這次要新增的索引，以及它服務的是哪個查詢
- **資料表關聯圖**，見下一節

DB 子單**一律用中文敘述描述結構，不要貼 SQL**。這一條有兩個理由：

- **讀者**：單子的讀者包含 PM 與需求方，`cHousehold IS NOT NULL OR cFloorFrom IS NOT NULL` 對他們是雜訊，「戶型、樓層起、樓層迄三個欄位不可同時為空值」才讀得懂。
- **送得出去**：部分站台在 Redmine 前方有 WAF，會把 SQL 樣式當成注入攻擊攔掉。被攔時 Redmine 完全沒收到請求，工具只回一句 `Error executing tool create_issue`，看不到 403 也看不到原因，很容易誤判成參數錯誤而反覆重試。

| 不要這樣寫 | 改成 |
|---|---|
| `cA IS NOT NULL OR cB IS NOT NULL` | 「cA 與 cB 不可同時為空值」 |
| `ALTER TABLE ... ADD ...` | 「既有表新增欄位」 |
| `sp_addextendedproperty` | 「加上欄位的中文說明」 |
| `int identity(1,1)` | `int`（自動遞增） |
| `CREATE INDEX IX_xxx ON ...` | 用索引表格列出名稱、欄位、服務的查詢 |

Markdown 表格、圍欄區塊、反引號、`tblXxx.cYyy` 這種欄位名都不受影響，照常使用。〈交付內容〉要提到 SQL 腳本時，寫「可重複執行的部署腳本，以不存在才建立的方式撰寫」即可，不要把腳本內容貼進單子——那屬於程式碼，本來就不該進需求單。

真的被擋住了：先用不含 SQL 片段的精簡內文把單子建起來取得單號，再用更新概述的方式補上改寫過的完整內容。

### DB 子單的資料表關聯圖

DB 子單的概述要畫一張**純文字**關聯圖，放在〈結構異動〉旁邊的圍欄區塊裡。用純文字是因為不能假設 Redmine 裝了會把文字算成圖的外掛——那類語法在沒裝外掛的站台只會原樣顯示成一堆看不懂的字。

圖要標出四件事：

- 一對多的方向（`1:n` 寫在箭頭上，箭頭指向多的那端）
- 這次**新增**的表與欄位，標上 `(新增)`
- 軟刪除、狀態、租戶／站台這類「不帶就會撈到不該撈的資料」的過濾條件
- 沒有實體外鍵、關聯只靠程式維護的地方

```
TblMember ──1:n──> TblOrder ──1:n──> TblOrderDetail
                       │              （無實體外鍵，關聯只靠程式維護）
                       └─ 查詢一律帶 IsDeleted = 0

TblUser   ──1:n──> TblOrderExport (新增)
```

**圖不取代條列，不可只有圖。** 圖給的是概觀，欄位對欄位的精確關聯仍要條列在圖的下方，與〈涉及的資料表〉同在這張子單的概述裡（兩章的寫法見 `references/feature_request/assess.md`）。資料表在開發過程改了就回頭重畫這張圖——它跟概述一樣是活文件，永遠只有一份。

## 標題

```
<使用者角色／功能>：<新增什麼能力>
```

冒號前是誰要用或哪個模組，冒號後是這個能力本身，動詞要具體。

**範例：**

- `後台管理者：可批次匯出指定期間的訂單明細`
- `會員中心：新增訂單狀態變更的信件通知`

反例：`匯出功能`（誰用？匯出什麼？做到哪裡算完？）。

## 排版格式

單子內文一律用 **Markdown**，不要用 textile。`h3. 標題` 這類 textile 語法在 Markdown 站台會原樣顯示成純文字，反而更難讀。

- 章節標題用 `##`；靠標題階層分段，不要用連字號分隔線。
- 欄位名、參數、狀態值用反引號；畫面文案或訊息原文用圍欄區塊。
- 條列用 `-`，操作流程才用 `1.`。

## 內文骨架

前三章必填。後四章**有事實才寫**——開單當下多半還寫不出來，之後查到或討論定案了再回頭補進概述；沒有內容就整段拿掉，不要留空標題。

**不要為了填滿而猜**：猜出來的相依與排除事項會被當成有人確認過的，比留白更糟。

````markdown
## 背景與目的

<誰、在什麼情境下、遇到什麼不便；做了這件事之後會變成怎樣>

## 需求內容

<要新增的能力：進入點、操作流程、資料範圍、規則>

## 驗收標準

<可驗證的條列：誰做什麼動作，會看到什麼結果>

## 影響範圍與相依

<會動到哪些既有功能、需要哪些前置條件或外部資源>

## 結構異動

新增或修改的每一張表各一段：表名一句用途，接一張逐欄位的表格。

**<資料表名>**：<這張表裝什麼，一句話>

| 欄位 | 型別 | 可否為空 | 預設值 | 中文說明 |
|---|---|---|---|---|
| `<欄位名>` | `<型別>` | not null／null | `<預設值>`／無 | <這個欄位裝什麼、值域或對到哪張表> |

<既有資料怎麼補：留空、回填預設值，還是要跑一次資料轉換>

## 不在範圍內

<明確排除、這次不做的事>

## 待確認

<需要需求方拍板才能定案的部分>
````

## 自我檢查

送出前逐項確認；每一項的展開說明在下面各節：

- [ ] 骨架整份寫在概述（`description`）欄位，沒有拆散到其他欄位
- [ ] 追蹤標籤與專案填的是查該站清單換到的 id，預計完成日是問出來的、不是自行推定的
- [ ] 標題兩段齊全（誰／哪個模組、新增什麼能力），動詞具體
- [ ] 內文是 Markdown：章節用 `##`，欄位名用反引號，沒有 textile 語法或連字號分隔線
- [ ] 背景寫的是可判斷的結果，不是「提升效率」這類形容詞
- [ ] 需求內容描述「要做什麼」而非「怎麼實作」，且涵蓋規則與邊界
- [ ] 每條驗收標準都能一次判定通過或不通過
- [ ] 錯誤與邊界情境（無資料、超上限、權限不足）都有對應條目
- [ ] 後四章寫的都是查到或討論定案的事實，沒有「應該／可能／通常」這類推測句
- [ ] 這次討論改到的需求已經更新回概述，不是只留在註記或對話裡
- [ ] 新功能開發已拆成母單＋UI／API／DB 三張子單，三張都建了，且各自掛在正確的父任務底下
- [ ] 母單只留跨層驗收條目，沒有重述各層細節；各層子單都有自己的驗收標準
- [ ] 這次不動的那一層仍開了子單，並寫明本次不動及原因
- [ ] 〈結構異動〉是逐欄位的表格，五欄（欄位、型別、可否為空、預設值、中文說明）都填了，中文說明不是重述欄位名
- [ ] DB 子單的概述有純文字資料表關聯圖，標了一對多方向、新增的表與欄位、必帶的過濾條件與無外鍵之處
- [ ] DB 子單全篇以中文敘述描述結構，沒有 SQL 條件式、DDL 或系統預存程序（讀者含非 IT，且部分站台的 WAF 會攔）
- [ ] 關聯圖下方仍有欄位對欄位的條列，不是只有圖
- [ ] 不確定的地方標了「未確認」，沒有留白
- [ ] 必填內容都來自需求方提供，缺的部分是問出來的，不是你補的猜測
- [ ] 沒有空章節，也沒有為了填滿而猜的內容

## 資訊不足時：用問答補齊

提需求的人多半不是 IT。必填章節的資訊不夠時，**不要自己填、不要留白，也不要把骨架丟回去叫對方填**——直接在對話裡問。

- **一次只問一題**，問完等回覆再問下一題。一次丟五個問題，通常只會拿回第一題的答案。
- **盡量給選項**讓對方用選的，並且永遠留一個「不知道」。
- **用日常語言問，不要用章節名**。不要問「驗收標準」，問「做好之後，你會怎麼確認它符合你要的？」；不要問「規則與邊界」，問「一次最多能做幾筆？沒有資料的時候該顯示什麼？」
- **相依與範圍排除不問**。那是查得出事實的人才寫得出來的，之後補進概述，不要為此多問一輪。
- **必填到齊就停筆**。單子開得快比寫得漂亮重要。
- 對方答「不知道」就照實寫「未確認」，不要替他猜；要需求方拍板的事寫進〈待確認〉。

## 各章節怎麼寫

### 背景與目的

先講**誰在什麼情境下遇到什麼不便**，再講做完之後會變成怎樣。目的要寫成可以判斷的結果，不要寫成形容詞。

寫「財務每月要人工從三張報表拼出對帳資料，約耗時兩小時」，不要寫「提升作業效率」。前者能在驗收時回頭對照，後者不能。

兩三句就夠。這一段是給日後翻單的人看的：功能為什麼存在。

### 需求內容

描述**要做什麼**，不描述**怎麼實作**。技術選型是 RD 的判斷，寫死在需求單裡只會綁住人；但需求本身的規則不能省：

- **進入點**：從哪裡開始用（哪個選單、哪個畫面、哪個按鈕）。
- **操作流程**：使用者依序做什麼，系統依序回應什麼。
- **資料範圍**：涵蓋哪些資料、以什麼條件篩選、要不要分權限。
- **規則與邊界**：數量上限、期間限制、重複執行會怎樣、沒有資料時顯示什麼。

最後兩項最常被漏掉，也最常在開發到一半才回頭補問。**不確定的地方就寫「未確認」，不要留白**——留白會被當成沒有限制。

### 驗收標準

這是整張單最重要的一段。每一條都要能被**做一次就判定通過或不通過**：

```markdown
- 管理者於訂單列表選取多筆訂單後點「匯出」，可下載含所選訂單的 CSV
- 未選取任何訂單即點「匯出」時，顯示提示訊息且不產生檔案
- 一般客服角色看不到「匯出」按鈕
- 匯出筆數超過 10,000 筆時，顯示提示並中止
```

寫成這樣，驗收時逐條走一次就有結論。反例是「匯出功能正常運作」「使用者體驗良好」——這種句子在驗收會議上只會變成各說各話。

**錯誤與邊界情境要有條目**，不能只列 happy path：沒有資料、超過上限、權限不足、重複操作，各自應該發生什麼。

評估過程中才查得出來的判準——**被擠到的既有功能之回歸確認、相依前置到位後才成立的條目、規模與邊界上限**——查到之後直接補進這一節，不要另外開一份驗收清單。同一張單上有兩份判準，驗收的人不知道該信哪一份。

### 影響範圍與相依

開單當下通常是空的，查過之後再補：

- **會動到哪些既有功能**：新增的東西擠進既有畫面或流程時，原本的行為會不會變。
- **前置條件與外部相依**：需不需要新的權限設定、第三方服務、資料匯入，或另一張單先完成。相依的單要寫單號。

這一節的每一項都會被下游當成有人查過，所以下筆前先問自己：**這件事我是查到的，還是推出來的？** 讀過原始碼、查過資料筆數、翻過既有單號、需求方明確講過，才算事實。推出來的東西只有兩條路——去查證，或整項不寫。**不要折衷寫成「可能會影響」**：那句話會讓讀的人以為有人看過了，於是他也不查，比留白更糟。

### 結構異動

要新增或修改的表與欄位放這裡，**一張表一段、逐欄位用表格列**。表格的五欄固定不變——欄位、型別、可否為空、預設值、中文說明——缺哪一格就是空白，比條列漏寫一項容易發現得多。

**中文說明不可省**：欄位名看不出它裝什麼，而讀這張單的不只有寫程式的人。說明要寫這個欄位裝什麼、值域是什麼、或對到哪張表的哪個欄位，不要重述欄位名（`ExportTime` 寫「匯出時間」等於沒寫，寫「這次匯出的執行時間，寫入後不再變更」才有資訊）。

```markdown
**TblOrderExport**：匯出紀錄，每次成功匯出寫一筆

| 欄位 | 型別 | 可否為空 | 預設值 | 中文說明 |
|---|---|---|---|---|
| `ExportId` | `int` identity | not null | 無 | 主鍵，流水號 |
| `MemberId` | `int` | not null | 無 | 匯出者，對 `TblMember.MemberId` |
| `ExportTime` | `datetime` | not null | `getdate()` | 這次匯出的執行時間，寫入後不再變更 |

**TblOrder**（既有表，新增欄位）

| 欄位 | 型別 | 可否為空 | 預設值 | 中文說明 |
|---|---|---|---|---|
| `LastExportTime` | `datetime` | null | 無 | 這筆訂單最後一次被匯出的時間；既有資料留 null，不回填 |
```

**既有資料怎麼處理一定要寫**：留空、回填預設值、還是要跑一次資料轉換。這一項漏掉，上線當天才會有人問。

型別或預設值在開發過程改了，**回頭改這一章**，不要用註記追加第二版——註記只能新增，兩版並存時接手的人得自己猜哪版算數。沒有結構異動就整段刪掉。

### 不在範圍內

明確寫出**這次不做**的事，尤其是討論過程中被提到、但決定延後的部分。

這一段的作用是防止驗收時範圍擴張：沒寫下來的排除，事後很難主張。若某項是「之後另開單處理」，就直接這樣寫。

這節寫的是**這次不做**，〈驗收標準〉寫的是**做完要通過什麼**，兩者不要混。某項排除只要寫進這裡就夠，不用再列成驗收條目。

### 待確認

需要需求方拍板才能定案的部分放這裡，把選項與各自的影響講清楚，明確提問。

**拍板之後要回來收尾**：把結論寫進〈需求內容〉或〈驗收標準〉，並把這一條從〈待確認〉刪掉。留著已經有答案的待確認事項，下一個讀單的人還會再問一次。全部確認完就整段刪掉。

## 語氣與用字

- 全篇繁體中文；欄位名、參數、狀態值、路徑維持原樣不翻譯。
- 描述需求，不描述實作。寫「可依期間篩選訂單」，不寫「加一個 date range 參數到查詢 API」。
- 具體數值優先於形容詞：寫「單次最多匯出 10,000 筆」而不是「不要太多筆」。
- 半形括號留給程式碼，全形括號留給中文。

## 送出

標題進 Redmine 的「主題」欄位，上面那份骨架**整份**進「概述」欄位。不要把章節拆散塞進自訂欄位。

需求後續有異動時，**回頭編輯概述**，不要用註記堆疊過程資訊。涉及的資料表與其關聯不走註記，寫在 DB 子單的概述（見 `references/feature_request/assess.md`）。

追蹤標籤選「新需求」，專案取需求所屬系統對應的專案。

新功能開發要建四張單：先建母單取得單號，再依序建 UI／API／DB 三張子單，各自把母單單號填進「父任務」欄位。子單的追蹤標籤同樣選「新需求」，專案與母單相同。

追蹤標籤與專案在單子上是 id，不是名稱：透過 API 或工具開單時要先查**該站**的清單，把名稱對成那個站的 id。各站的 id 體系彼此獨立，不要憑記憶填數字，也不要沿用別站查到的 id。

預計完成日（`due_date`）由需求方或 PM 決定，透過工具開單時是必填欄位：不知道就在對話裡問，給選項讓對方選（例如「這週內／這個月底／沒有特定期限」），**不要自行推定一個日期**——推定出來的日期會被下游當成需求方答應過的期限。

怎麼交付依你手上有什麼：能直接寫進 Redmine 就照上面的落點寫，寫完把單號與網址回報給使用者；不能就把標題與內文分成兩塊輸出在對話裡，讓使用者自己貼。兩種都一樣，送出前先讓使用者確認——開單是對外動作，不要自作主張。
