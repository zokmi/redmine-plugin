# Redmine 臭蟲診斷格式

依 SKILL.md 的共用落點、提問與交付規則。需要領域澄清、跨專案引用或寫法範例時才讀 `diagnose-details.md`。
主題：`<受影響的對象>：<技術根因>，<使用者可見後果>`。

## 事實與落點

- 先讀實際原始碼確認路徑、行號、列舉與觸發條件；也查同源問題與固化錯誤的測試。
- 註記只補機制、概述看不出的前置狀態、修正方向與參考，不重述現象、步驟或預期結果。
- 驗收與需求面待確認追加到概述對應章節，不放註記；保留回報者原有現象、步驟與判準。
- 判準涵蓋既有壞資料修復、同源問題處理、錯誤測試修正；改法可換，判準不可少。
- 無既有單時，先讀 report.md 建現象與驗收，再追加診斷。只改主題不代表可以改寫概述。
- 問題依嚴重度排序，單一問題不必編號；概念未混淆就刪摘要，影響更正僅在推翻原描述時寫。
- 位置獨立一行；代碼貼最小可理解範圍（通常 3–5 行）並標語言；列舉同列數字與中文名。
- 描述事實不評價人；碰巧正確但語意有誤仍明說；未驗證不寫成事實。
- 修正給方向、理由與判準，不貼完整實作；受害欄位不可當作可靠判斷依據。
- 跨專案參考註明差異，不能照搬；優先權改欄位，不寫一節急迫度。

## 自我檢查

交件前逐項確認；每一項的展開說明在下面各節：

- [ ] 註記只寫機制、觸發條件、修正方向與參考，沒有夾帶該回寫概述的內容
- [ ] 標題三段齊全（對象、機制、後果），能被搜尋到關鍵欄位名
- [ ] 內文是 Markdown：章節用 `##`／`###`，程式碼用圍欄區塊，沒有 textile 語法或連字號分隔線
- [ ] 每個檔案路徑與行號都實際讀過原始碼確認，不是憑印象
- [ ] 沒有重述概述已有的現象、操作步驟與預期／實際結果
- [ ] 觸發條件帶具體欄位值與列舉值，是概述看不出來的那一段
- [ ] 影響只在診斷結果與概述不同時才寫，且誠實，沒有誇大也沒有輕描淡寫
- [ ] 檢查過同樣寫法是否擴散到別處、是否有測試固化了錯誤行為
- [ ] 建議修正給的是方向與判準，不是整段實作
- [ ] 診斷才看得出來的驗收判準已補進**概述**的〈驗收標準〉，每條都能一次判定通過或不通過
- [ ] 需要需求方拍板的事已寫進**概述**的〈待確認〉，沒有藏在註記的敘述裡
- [ ] 概述改動幅度大時，註記有一句話說明概述改了什麼
- [ ] 沒有空章節
