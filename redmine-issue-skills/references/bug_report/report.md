# Redmine 臭蟲單文案格式（回報階段）

這份格式給**發現問題、但沒有讀過相關原始碼的人**——PM、客服、測試。你要提供的是「發生了什麼」與「有多嚴重」，不是「為什麼會這樣」。根因與建議修正由接手的 RD 診斷後補上。

一張好的回報單只有一個判準：**RD 不必回頭問你，就能自己重現。**

## 標題

```
<受影響的功能>：<使用者遭遇的後果>
```

**範例：**

- `客戶匯出對帳報表：金額比實際少，財務無法對帳`
- `會員登入頁：輸入正確密碼仍顯示帳號或密碼錯誤`

反例：`報表有問題`（沒有功能、沒有後果，逼人點進來才知道嚴不嚴重）。

RD 診斷出機制後會把標題補成三段（對象、技術根因、使用者可見後果），那是他的事，你不必先猜。

## 排版格式

單子內文一律用 **Markdown**，不要用 textile。`h3. 標題` 這類 textile 語法在 Markdown 站台會原樣顯示成純文字，反而更難讀。

- 章節標題用 `##`；靠標題階層分段，不要用連字號分隔線。
- 錯誤訊息原文用三個反引號的圍欄區塊貼上，保留原始換行。
- 條列用 `-`，操作步驟才用 `1.`。

## 內文骨架

前三章必填——缺哪一個，RD 就得回頭問你。標「選填」的沒有就整段拿掉，**不要為了填滿而猜**：猜錯會把 RD 帶往錯的方向，比留白更糟。

〈待確認〉這一章多半由 RD 診斷後追加，回報時寫不出來很正常；骨架先留著位置，是為了讓回寫的人知道該加在哪。

**急迫度不寫成內文**。誰受影響、多常發生，直接反映在單子的「優先權」（`priority_id`）欄位上，內文不再另寫一節——同一件事寫兩處，排序的人只會看欄位，文字那份遲早過期。

````markdown
## 問題描述

<一兩句：哪個功能、什麼情況下、發生什麼事>

<同一節接著補這兩件，知道就寫、不知道就略過：有沒有資料被寫錯或遺失、有沒有替代做法可以先擋著>

## 重現步驟

- 環境：<正式站／測試站，網址>
- 對象：<哪個帳號、哪個客戶、哪一筆資料>
- 時間：<發生時間，愈精確愈好>

1. <操作>
2. <操作>
3. 預期看到：<你認為正確的結果>
   實際看到：<畫面上真正出現的結果>

## 驗收標準

<可驗證的條列：誰做什麼動作，會看到什麼結果>

## 佐證（選填）

<截圖、錯誤訊息原文、相關單號或訂單編號。有附件上傳工具且已授權附圖時上傳並使用回傳附件資訊；工具不可用時請使用者手動附檔，內文說明圖片位置>

## 待確認（選填，多半由 RD 診斷後追加）

<要需求方拍板才能決定作法的部分。回報時通常寫不出來，整段拿掉即可>
````

## 自我檢查

送出前逐項確認；每一項的展開說明在下面各節：

- [ ] 骨架整份寫在概述（`description`）欄位，沒有拆散到其他欄位
- [ ] 追蹤標籤與專案填的是查該站清單換到的 id，預計完成日是問出來的、不是自行推定的
- [ ] 標題兩段齊全（受影響的功能、使用者遭遇的後果）
- [ ] 內文是 Markdown：章節用 `##`，錯誤訊息用圍欄區塊，沒有 textile 語法或連字號分隔線
- [ ] 重現步驟帶了環境、對象與時間
- [ ] 「預期看到」與「實際看到」分開寫，兩者都具體
- [ ] 回報者提到過資料被寫錯／遺失或有替代做法的話，寫進「問題描述」，沒提到就不追問也不猜
- [ ] 急迫度反映在「優先權」欄位上，沒有在內文另寫一節；優先權是依誰受影響、多常發生選的，沒有誇大也沒有輕描淡寫
- [ ] 驗收標準至少一條，且**每條**都能一次判定通過或不通過；寧可少寫，不要湊數
- [ ] 〈待確認〉沒東西寫就整段拿掉，不留空標題（它多半由 RD 診斷後追加）
- [ ] 若有寫佐證，是截圖、錯誤訊息原文或相關單號；附件依工具能力與授權處理，未上傳時只留文字說明，不捏造引用；沒有就整段拿掉
- [ ] 必填內容都來自回報者提供或你親眼所見，缺的部分是問出來的，不是你補的猜測
- [ ] 沒有猜測性的技術診斷，也沒有為了填滿而猜的內容

根因與建議修正由接手的 RD 診斷後寫成註記，這張單不必預留空章節。RD 另外會把診斷才看得出來的驗收判準補進〈驗收標準〉、要需求方拍板的事寫進〈待確認〉——概述會被追加，但你寫的現象與重現步驟不會被覆寫。

## 資訊不足時：用問答補齊

回報的人多半不是 IT。必填章節的資訊不夠時，**不要自己填、不要留白，也不要把骨架丟回去叫對方填**——直接在對話裡問。

- **每輪最多三個相關缺漏**，用日常語言與選項詢問；複雜或互相依賴時一次一題。已知資訊不重問。
- **盡量給選項**讓對方用選的，並且永遠留一個「不知道／沒注意」。
- **用日常語言問，不要用章節名**。不要問「重現步驟是什麼」，問「你當時是先點了哪裡、接著做了什麼？」；要判斷優先權時不要問「影響範圍」，問「這件事現在有多少人碰得到——只有你，還是整個部門都會遇到？」
- **選填章節不問**。對方沒主動提「佐證」就整段拿掉，不要為了完整而追加一輪。
- **必填到齊就停筆**。單子開得快比寫得漂亮重要，其餘的 RD 接手後查得出來。
- 對方答「不知道」就照實寫「未確認」，不要替他猜。

## 驗收標準怎麼寫

每一條都要能**做一次就判定通過或不通過**：誰做什麼動作，會看到什麼結果。

```markdown
- 依上述步驟以帳號 A001 匯出 2026-07 對帳報表，金額與訂單明細總和相符
- 既有已匯出的 6 月報表重新匯出後，金額同樣正確
- 沒有任何訂單的期間匯出時，顯示提示且不產生檔案
```

反例是「匯出功能正常」——驗收時只會變成各說各話。

這一段與重現步驟裡的「預期看到」分工不同：「預期看到」只針對你走過的那一條路徑；驗收標準是**整張單修好的判準**，通常還要涵蓋已經被寫壞的舊資料要不要一併修正、以及邊界情境（沒有資料、超過上限、權限不足）。寫不出邊界條目沒關係，把你確定的先列出來——**一條能一次判定的標準，勝過三條為了湊數而猜的**。邊界情境由接手的 RD 診斷後補齊。

## 三個規則

### 不知道就寫「未確認」

沒把握的事要標明沒把握，不要猜，也不要留白。留白會讓 RD 以為你確認過了，於是他也不查——這種漏洞最難發現。

### 「預期看到」與「實際看到」一定要分開寫

只寫「結果不對」是最常見的無效回報。兩者並列，RD 才知道你認定的正確行為是什麼；有時真正的分歧就在這裡——功能其實照規格運作，是規格與期待不一致，那不是缺陷而是需求問題。

### 不要診斷

不必猜是哪支程式、哪個欄位壞了。你的猜測會變成 RD 的起點，猜錯就是把人帶往錯的方向繞一圈，比不猜更糟。把現象講清楚已經是最有價值的部分。

## 語氣與用字

- 全篇繁體中文；錯誤訊息、欄位名、單號原樣照抄，不要轉述。
- 描述事實，不評價人。寫「送出後金額少了 500」，不寫「這功能爛透了」。單子會被很多人看到，包含原作者。
- 具體數值優先於形容詞：寫「等了約 30 秒」而不是「非常慢」。

## 送出

標題進 Redmine 的「主題」欄位，上面那份骨架**整份**進「概述」欄位。不要把章節拆散塞進自訂欄位，也不要拿這份骨架去寫註記；註記只寫這次新增的事實。

急迫度走「優先權」（`priority_id`）欄位，不進概述：依誰受影響、多常發生選一級，選項與各級名稱依站台設定，拿不定就照實選預設值，不要在內文補一段文字代替。

追蹤標籤選「臭蟲」，專案取問題所在系統對應的專案。

追蹤標籤與專案在單子上是 id，不是名稱：透過 API 或工具開單時要先查**該站**的清單，把名稱對成那個站的 id。各站的 id 體系彼此獨立，不要憑記憶填數字，也不要沿用別站查到的 id。

預計完成日（`due_date`）由需求方或 PM 決定，透過工具開單時是必填欄位：不知道就在對話裡問，給選項讓對方選（例如「這週內／這個月底／沒有特定期限」），**不要自行推定一個日期**——推定出來的日期會被下游當成需求方答應過的期限。

怎麼交付依你手上有什麼：能直接寫進 Redmine 就照上面的落點寫，寫完把單號與網址回報給使用者；不能就把標題與內文分成兩塊輸出在對話裡，讓使用者自己貼。送出前呈現具體文案；已有明確寫入授權就執行，否則取得確認。
