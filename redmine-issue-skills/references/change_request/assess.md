# Redmine 調整單評估註記格式

這份格式給**手上已有事實的人**——多半是接手的 RD，但需求方自己知道相依或既有資料狀況時同樣適用。判準是手上有沒有可寫的事實，不是你的角色。

概述（`description`）留給提出調整的人寫現況、調整內容與驗收標準。**註記只承載〈影響範圍〉**——那是你查證當下的事實快照，寫下來就不會再變。

查出來的驗收判準與需求面待確認**回頭寫進概述**，不放註記：那兩章會被勾、被調整、被答覆，而註記實務上只能新增、改不動，留在註記只會積成好幾份，讀的人不知道哪一份算數。落點見下方〈評估後要回頭更新概述〉。

一則好的評估註記只有一個判準：**看完的人知道這次異動會碰到什麼。**

## 下筆前：先把事實釘死

這則註記的每一項都會被下游當成有人查過。因此下筆前先問自己一句：
**這件事我是查到的，還是推出來的？**

算事實的：讀過原始碼、查過資料筆數、翻過既有單號、需求方明確講過。
不算事實的：「這種功能通常會影響到⋯⋯」「應該還有別的地方也用到」。

推出來的東西只有兩條路——去查證，或整項不寫。**不要折衷寫成「可能會影響」**：
那句話會讓讀的人以為有人看過了，於是他也不查，比留白更糟。

## 排版格式

同調整單概述：一律 Markdown，章節用 `##`，設定值與欄位名用反引號，條列用 `-`。不要用 textile，不要用連字號分隔線。

## 內文骨架

註記只有一章，而且是「有事實才寫」。查不出東西就不要送出這則註記。

````markdown
## 影響範圍

<會不會改變既有行為、既有資料要不要一併處理、有沒有其他功能跟著受影響>
````

## 自我檢查

送出前逐項確認；每一項的展開說明在下面各節：

- [ ] 註記只寫〈影響範圍〉，查出來的驗收判準與待確認已回寫概述
- [ ] 每一項都講得出「我從哪裡查到的」，沒有「應該／可能／通常」這類推測句
- [ ] 影響範圍的既有資料怎麼處理有明確交代
- [ ] 補進**概述**〈驗收標準〉的判準只列概述原本列不出來的，每條都能一次判定通過或不通過
- [ ] 要需求方拍板的事都寫進**概述**的〈待確認〉，沒有藏在註記的敘述裡
- [ ] 概述改動幅度大時，註記有一句話說明概述改了什麼
- [ ] 沒有空章節；查不出影響範圍時不送出這則註記

## 各章節怎麼寫

### 影響範圍

回答三件事，答得出來就寫，答不出來的那一項就不寫，不要猜：

- **既有行為會不會變**：使用者會不會看到不一樣的結果？會的話，要不要事先公告？
- **既有資料要不要處理**：改了規則之後，不符合新規則的舊資料怎麼辦——保留、轉換，還是擋在下次編輯時？這一項最常被漏掉，卻最常在上線後炸開。
- **有沒有連帶對象**：其他功能、報表、對外介接或排程有沒有依賴這個行為。

## 評估後要回頭更新概述

驗收的人只看概述。判準若是「概述一份、註記一份」，他不會知道還有第二份要讀；待確認留在註記，被答覆之後那句話還會一直掛著。因此查出來的這兩類內容**回頭寫進概述**：

| 查出來的東西 | 寫進概述哪一章 |
|---|---|
| 概述漏掉的驗收判準 | 〈驗收標準〉，接在原有條目之後 |
| 要需求方拍板才能定案的事 | 〈待確認〉；概述沒有這一章就新增在最後 |

- **直接改，不必保留沿革**。Redmine 自己有編輯歷程。
- **不要動提出者寫的現況與調整內容**。你是追加，不是重寫。
- **概述改動幅度大時，在註記寫一句「概述已更新：⋯⋯」**，讓關注者知道要重讀。

### 補進概述的驗收標準

概述已經有一份驗收標準了，這裡**只追加它列不出來的判準**——查過既有資料或環境設定才知道要驗的東西。每條同樣要能做一次就判定通過或不通過。

```markdown
- 不符新規則的 1,203 筆舊資料經轉換後，全數通過新規則檢核
- 依賴此設定的夜間排程照常執行，發送結果與異動前相同
- 測試站與正式站各自確認端點已改為 https（正式站未確認前不算完成）
```

這三類是評估才看得出來的：**既有資料的處理結果、連帶對象的回歸確認、各環境逐一確認**，不列進驗收就會被漏掉。反過來說「後台觸發簡訊，收件者收到簡訊」這種概述寫得出來的條目就不必再抄一次。

影響範圍那節寫「有 1,203 筆舊資料不符新規則」是陳述事實；這節寫「這 1,203 筆轉換後要全數通過檢核」是驗收判準。兩者分開，別把判準混在事實敘述裡。

### 寫進概述的待確認

技術上做得到、但**要不要這樣做得由需求方決定**的部分寫進概述的〈待確認〉。把選項與各自的影響講清楚，明確提問，別把疑問藏在註記的敘述裡讓人自行體會。

拍板之後回頭收尾：結論寫進〈調整內容〉或〈驗收標準〉，並把該條從〈待確認〉刪掉；全部確認完就整段刪掉。這正是它不能放註記的理由——註記刪不掉也改不了。

## 語氣與用字

- 全篇繁體中文；設定鍵名、路徑、欄位名、程式碼維持原樣不翻譯。
- 描述事實，不評價人。單子會被很多人看到，包含原作者。
- 具體值優先於形容詞：寫「約 1,200 筆舊資料不符新規則」而不是「有些舊資料會有問題」。
- 半形括號留給程式碼，全形括號留給中文。

## 送出

上面那份骨架**整份**進「新增註記」欄位。

- **除了上面那兩類回寫，不要動概述。** 那是需求方的入口，覆寫掉等於把非 IT 讀者趕走。
- **沒有事實可寫就不要追加註記。** 註記會通知關注者，一則空模板比不寫更擾人。
- 標題需要修正時只改「主題」欄位，不要順手帶上概述。

怎麼交付依你手上有什麼：能直接寫進 Redmine 就照上面的落點寫；不能就把內容輸出在對話裡，讓使用者自己貼。兩種都一樣，送出前先讓使用者確認——追加註記會通知關注者，是對外動作。
