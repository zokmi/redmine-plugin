# 撰寫 Redmine 單子

公司對三種單別有各自的標準格式。**先判單別與階段，讀對應的骨架，再依它撰寫** ——
不要憑印象寫，也不要把三種格式混用。

## 落點對照表

逐項列舉，不必自行推論：

| 單別與階段 | 讀這份骨架 | 內容貼到 Redmine 的 |
|---|---|---|
| `bug+report` | `references/bug_report/report.md` | 概述 |
| `bug+diagnose` | `references/bug_report/diagnose.md` | 新增註記（驗收判準與待確認補進概述） |
| `change`（省略階段） | `references/change_request/change.md` | 概述 |
| `change+assess` | `references/change_request/assess.md` | 新增註記 |
| `feature`（省略階段） | `references/feature_request/feature.md` | 概述 |
| `feature+assess` | `references/feature_request/assess.md` | DB 子單的概述（資料表與關聯兩章） |

「概述」是 Redmine 建單／編輯畫面上的大內文欄位；「新增註記」是單子下方追加留言的
欄位。**bug 與 change 的後段內容（diagnose、change+assess）不覆寫概述** —— 概述是
給非 IT 讀者的入口，覆寫掉等於把他們趕走。

**驗收標準與待確認一律只在概述**，三種單別皆同。那兩章會被勾、被調整、被答覆，而註記實務上
只能新增、改不動；留在註記就會積成好幾份，讀的人不知道哪一份算數。後段（diagnose／assess）
查出來的判準接在概述的〈驗收標準〉之後，要需求方拍板的事寫進〈待確認〉（沒有這一章就新增），
其餘章節仍然只在註記，回報者／提出者寫的內容不動。

**新需求（feature）是例外，它沒有註記落點**：概述是活文件，需求後續怎麼改、範圍縮到哪、
相依查到什麼、哪個判準拍板了，一律回頭更新概述，維持成這張單目前最新的樣子。資料表、
關聯與結構異動也不走註記——那一層有自己的 DB 子單，全部寫在該子單的概述裡。註記最多用來
說一句「概述已更新」，提醒關注者重讀。

## 怎麼判單別

判準是**有沒有「現況」可改**：

- **bug（臭蟲）** —— 功能壞了、行為與預期不符。
- **change（調整）** —— 既有功能要改成別的樣子：設定值、規則、文案、版面、流程的異動。
- **feature（新需求）** —— 系統目前沒有、要新增的能力。

既有功能換個樣子是 change，從無到有是 feature，壞掉才是 bug。

**feature 若是新功能開發**（要寫程式才做得出來的新能力），除母單之外必須再開 UI、API、DB
三張子單，各自掛在母單底下並各寫該層的內容；三張是下限，工作量大時可再往下拆。怎麼拆、
各層寫什麼、DB 子單的資料表關聯圖怎麼畫，見 `references/feature_request/feature.md` 的
〈新功能開發要拆子單〉那一節。

對應 Redmine 站上的追蹤標籤名稱：`bug`→臭蟲、`change`→調整、`feature`→新需求。

## 怎麼判階段

判斷依據一律是**你手上有沒有事實**，不是你的角色。

- **`bug` 必須指定階段**，兩者是同一張單的前後段，不可預設任一個：
  - `report` —— 你只觀察到現象、沒讀過相關原始碼（PM／客服／測試回報）。
  - `diagnose` —— 你已實際讀過原始碼，要寫出根因與建議修正；查出來的驗收判準與需求面
    待確認一律補進概述。
- **`change` 與 `feature` 的階段可省略**：
  - 省略 —— 取得概述骨架（給需求方看的必填章節）。
  - `change+assess` —— 取得評估註記模板，註記只寫〈影響範圍〉這類查證當下的事實快照；
    查出來的驗收判準與待確認回頭補進概述。
  - `feature+assess` —— 取得〈涉及的資料表〉〈資料表關聯〉兩章的寫法，內容寫進 **DB 子單的
    概述**。新需求的其餘評估內容（影響範圍與相依、結構異動、不在範圍內、待確認）查到之後
    一律**補進概述**（結構異動在 DB 子單，其餘在母單），都不走註記。

## 資訊不足時

開單的人多半不是 IT。必填章節的資訊不夠時，**不要自己填、不要留白，也不要把骨架丟回
去要對方填** —— 在對話裡問，一次只問一題，盡量給選項並永遠留一個「不知道」，用日常語
言問而不用章節名。選填章節不問。必填到齊就停筆。對方答「不知道」就照實寫「未確認」。

各份骨架裡都有這一節的完整版，依它執行。

## 交付

寫完之後**先印在對話裡**，分成兩塊讓使用者各自複製：

1. **主題**（Redmine 的標題欄位）—— 一個圍欄區塊，只有一行。
2. **概述** 或 **新增註記**（依落點對照表）—— 另一個圍欄區塊，整份骨架的內容。

印完再問一句要不要存成檔案。不要自作主張存檔，也不要把兩塊併成一塊。

**截圖與附件**：這裡沒有上傳能力。如果使用者提供了截圖，交付時明確告知「這幾張圖請你
自己拖進 Redmine 的附件區」，並在內文對應位置留一行文字說明那張圖是什麼。不要假裝已經
上傳，也不要自己寫 `![](檔名)` —— 那個檔名在 Redmine 上還不存在，圖片會是破的。

## 骨架在哪

`references/` 與這份 SKILL.md 同一層。若你是透過一行指標被指到這裡的（沒有原生 skill
機制的 harness），骨架就在 `~/.redmine-issue-guides/references/` 底下。
